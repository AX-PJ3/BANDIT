# 기준 작성 원칙 (초안 v0.1)

> **이 문서는** 팀 위키에 무엇을, 어떤 크기와 모양으로 적을지 정한 규칙이에요. 사람도 AI도 이 원칙대로 기준을 쓰고 고쳐요.
> **상태:** 초안. 10/9 호윤님·부건님이 확정하고, 정민님이 데이터 구조와 맞는지 검토해요 (Linear SIL-6).
> **고칠 때:** 이 원칙을 바꾸는 것도 기준 변경이에요. CHANGELOG에 한 줄 남겨요.

---

## 1. 무엇이 기준인가요

**기준은 두 사람 이상의 결과물에 영향을 주는 결정이에요.**

한 사람이 바꿨을 때 다른 사람의 화면, 코드, 문구, 테스트, 숫자가 달라져야 한다면 기준이에요.

| 기준이에요 | 기준이 아니에요 |
|---|---|
| 주문 응답의 쿠폰 값은 비어 있을 수 있다 | 쿠폰 값을 담는 변수 이름 |
| 터미널 알림은 한 번에 변경 하나만 보여 준다 | 알림을 그리는 함수의 구조 |
| 주 지표는 "몰랐다"고 답한 변경 수다 | 오늘 회의 시간 |
| 기준 ID는 `영역.주제.규칙` 형식이다 | 누가 어떤 이슈를 맡았는지 (Linear에 있어요) |
| 앱 알림 제목은 40자 이하다 | 지금 진행 중인 작업 상태 (Linear에 있어요) |

### 헷갈릴 때 묻는 질문 3개

1. **이게 바뀌면 다른 사람이 다시 해야 하는 일이 생기나요?** 예 → 기준
2. **AI가 이걸 모르고 작업하면 틀린 결과물을 만들까요?** 예 → 기준
3. **한 달 뒤에도 의미가 있나요?** 아니오 (오늘 할 일, 진행 상황) → Linear에 적어요

---

## 2. 한 기준에 규칙 하나

- 기준의 **값**은 한 문장으로 끝나요.
- 값에 "그리고", "또한", "단,"이 들어가면 기준을 둘로 나눠요.
- 예외가 있으면 예외도 별도 기준으로 만들어요.

| 나쁜 예 | 좋은 예 |
|---|---|
| 쿠폰 값은 비어 있을 수 있고, 비어 있으면 화면에 "쿠폰 없음"을 보여 준다 | `order.coupon.nullable`: 쿠폰 값은 비어 있을 수 있다<br>`order.coupon.empty-label`: 쿠폰 값이 비어 있으면 "쿠폰 없음"을 보여 준다 |

**왜:** 알림은 기준 단위로 가요. 기준이 크면 관계없는 사람에게도 알림이 가서 "관계없다" 비율(보호 지표)이 올라가요.

---

## 3. ID 짓는 법

형식: **`영역.주제.규칙`** (영문 소문자, 숫자, 하이픈만)

| 부분 | 규칙 | 예 |
|---|---|---|
| 영역 | 아래 영역 코드 중 하나 | `notify` |
| 주제 | 그 영역 안의 대상 (명사) | `terminal` |
| 규칙 | 무엇을 정했는지 (짧은 말) | `one-change` |

- 한 번 정한 ID는 **절대 바꾸지 않아요.** 내용이 바뀌면 버전만 올려요.
- 뜻이 완전히 달라지면 새 ID를 만들고, 이전 기준은 "폐기"로 바꾸고 대체한 ID를 적어요.
- 예전 문서의 `RULE-COUPON-NULL`, `MOL-7` 같은 표기는 옛 형식이에요. 위키에는 쓰지 않아요.

### 영역 코드 (초안)

| 코드 | 영역 | 파일 | 담는 것 |
|---|---|---|---|
| `goal` | 문제와 목표 | `문제와-목표.md` | 문제 정의, 대상 사용자, 목표, 지표 정의 |
| `wiki` | 기준 모으기 | `기능-기준모으기.md` | 위키 저장, 버전, 조회, 되돌리기, 잠금 |
| `detect` | 바뀐 기준 찾기 | `기능-바뀐기준찾기.md` | PR 읽기, 걸러 내기, 판단, 안전 규칙 |
| `notify` | 담당자에게 알리기 | `기능-알리기.md` | 이슈 연결, 영향 찾기, 터미널 알림, 응답, 예외 |
| `app` | 데스크톱 앱 화면 | `앱-화면.md` | 화면, 앱 알림 문구, 설치 |
| `data` | 데이터 구조 | `데이터-구조.md` | 표, 칸, ID 형식, 상태 값 |
| `copy` | 문구와 말투 | `문구.md` | AI 설명 문장 규칙, 용어 통일, 말투 |
| `work` | 일하는 방식 | `일하는-방식.md` | 브랜치, 리뷰, 기록 규칙처럼 결과물에 영향을 주는 팀 규칙 |

영역은 **8개 이하**로 유지해요. 영역 하나에 기준이 50개를 넘으면 나누는 걸 검토해요. (`wiki.area.max-standards`)

## 4. 기준 하나에 꼭 있어야 하는 칸

| 칸 | 필수 | 쓰는 법 |
|---|---|---|
| ID | 필수 | 위 형식 |
| 제목 | 필수 | 누구나 읽을 수 있는 한 문장, 40자 이하. 개발 용어 대신 쉬운 말 |
| 값 | 필수 | 정한 내용 한 문장. 확인할 수 있게 구체적으로 (숫자, 이름, 조건) |
| 이유 | 필수 | 왜 이렇게 정했는지 한 문장 |
| 적용 범위 | 선택 | `코드:` 경로 / `API:` / `화면:` / `문서:` 중 하나 이상. 바뀐 기준 찾기와 알림의 열쇠예요 |
| 근거 | 선택 | 어디서 정해졌는지: PRD 섹션, PR 번호, 회의 날짜, Figma 링크 |
| 항상 적용 | 필수 | `예` / `아니오` |
| 상태 | 필수 | `사용` / `폐기` |
| 대체 | 폐기일 때 필수 | 이 기준을 대체한 ID |
| 버전 | 필수 | 1부터 시작해 바뀔 때마다 1씩 |
| 잠금 | 선택 | `예`면 AI가 고치지 못해요. 사람이 정해서 꼭 지켜야 하는 것만 |

### 적용 범위를 쓰는 요령

- 아직 코드가 없으면 **만들어질 위치를 예상해서** 적어요. (예: `코드: packages/cli/src/brief/**`) 저장소 구조(SIL-16)가 정해지면 고쳐요.
- 화면은 앱 화면 이름 그대로 (`화면: 나에게 온 변경`).
- 너무 넓게 쓰지 않아요. `코드: src/**`처럼 쓰면 모든 PR에 걸려서 의미가 없어요.

---

## 5. 문장 쓰는 법

- 제목과 값은 **"~이다 / ~한다"로 끝나는 평서문**이에요. (해요체는 알림 문구에서만 써요)
- 제목만 읽어도 무엇을 정했는지 알 수 있게 써요. "쿠폰 관련" (X) → "쿠폰 값은 비어 있을 수 있다" (O)
- 개발 용어는 꼭 필요할 때만, 처음 나오면 괄호로 풀어요. "null(비어 있음)"
- "적절히", "가능하면", "필요시" 같은 말은 쓰지 않아요. 확인할 수 없어요.
- 숫자는 단위까지 적어요. "짧게" (X) → "40자 이하" (O)

---

## 6. 항상 적용되는 기준

- 모든 작업에 매번 지켜야 하는 기준만 `항상 적용: 예`로 해요. **위키 전체에서 10개까지.**
- AI는 세션을 시작할 때 이 기준만 미리 읽고, 나머지는 필요할 때 찾아 읽어요.
- 10개가 넘으면 덜 중요한 것을 `아니오`로 바꿔요.

예: 기준 ID 형식, 기준을 바꾸면 CHANGELOG에 남기기, 쉬운 말 쓰기, 삭제하지 않고 폐기하기.

---

## 7. 바꾸고, 폐기하고, 되돌리기

| 상황 | 하는 일 |
|---|---|
| 값이 바뀜 | 값·이유·근거를 고치고 버전 +1. 이전 값은 CHANGELOG에 남아요 |
| 더 이상 안 씀 | 상태를 `폐기`로, 대체 ID 적기. **지우지 않아요** |
| 이전 값으로 돌아감 | 이것도 새 버전이에요. 이유에 "v1로 되돌림" 적기 |
| 둘로 나뉨 | 새 ID 두 개를 만들고, 원래 기준은 폐기 + 대체에 두 ID |

모든 변경은 CHANGELOG에 한 줄 남겨요. (형식: `02-형식/CHANGELOG-템플릿.md`)

## 8. 결정 전 체크리스트 (기준 하나 쓸 때)

- [ ] 두 사람 이상의 결과물에 영향을 주나요?
- [ ] 값이 한 문장이고 "그리고"가 없나요?
- [ ] 제목만 읽어도 무엇을 정했는지 알 수 있나요?
- [ ] 적용 범위가 구체적인가요? (`src/**` 같은 넓은 범위 아님)
- [ ] 근거를 따라가면 원래 결정을 찾을 수 있나요?
- [ ] 같은 내용의 기준이 이미 있지 않나요? (INDEX와 검색으로 확인)

## 9. 아직 정하지 않은 것 (킥오프 후 확정)

- 영역 코드 8개가 맞는지 (`copy`, `work`를 따로 둘지)
- 디자인 결정(Figma)의 적용 범위를 어떻게 쓸지: `화면:` + Figma 링크?
- 잠금은 누가 걸 수 있는지 (DRI만?)
- 같은 기준을 두 사람이 동시에 고치면 어떻게 할지 (SIL-15에서 정해요)
