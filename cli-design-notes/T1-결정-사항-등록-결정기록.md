## 1. 이 화면이 하려는 일 (의도)

| 의도                                     | 어떻게 지키나                                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **결정 사항이 조용히 달라지지 않는다**   | 작업 중에 결정 사항과 다른 값을 쓰게 되면 Claude가 먼저 "이걸 등록할까요?"를 물어요(위키 `work.wiki.ask-before-change`, SIL-66) |
| **사람이 직접 바꿀 때도 같은 길로 간다** | 사람이 "결정 사항 바꿔 줘"라고 하면 확인 단계를 건너뛰고 조사 결과부터 보여 줘요                                                |
| **무엇과 부딪히는지 알고 등록한다**      | 등록하기 전에 관련 결정 사항을 찾아 보여 줘요. 같은 것을 정한 결정 사항과 어긋나는 결정 사항을 나눠 보여 줘요                   |
| **사람은 고르고 고치기만 한다**          | 제목·값·이유·항상 적용은 Claude가 정리해 넣어요. 사람은 등록될 모습을 보고 등록하기 / 수정하기 / 취소하기 중에서 골라요         |
| **모든 작업에 들어가는 값은 꼭 본다**    | 항상 적용 여부는 Claude가 정하되, 예든 아니오든 따로 한 줄로 굵게 보여 줘서 틀리면 바로 고치게 해요                             |
| **등록했는지 확실히 안다**               | 저장한 뒤 `✓ 결정 사항을 등록했어요.`와 누구에게 알렸는지를 보여 줘요                                                           |

## 2. 결정한 흐름

```
[경우 1] Claude가 알아챔                 [경우 2] 사람이 "결정 사항 바꿔 줘"
          │                                             │
① 확인   이걸 결정 사항으로 등록할까요?                  │
          ├ 아니요 → 등록하지 않고 하던 작업을 이어감      │
          └ 예 ──────────────────┐                      │
                                 ▼                      ▼
② 조사 결과   Claude가 관련 결정 사항을 찾아봄 (search_standards)
          ├ 충돌 없음 → "충돌하는 결정 사항이 없어요." ─────────────┐
          └ 충돌 있음 → 바뀌는 결정 사항 · 어긋나는 결정 사항을 보여 줌 │
                        이대로 바꿀까요?                            │
                          ├ 아니요 → 등록하지 않고 작업을 이어감     │
                          └ 예 ──────────────────────────────────┤
                                                                   ▼
③ 등록될 모습   제목 · 값 · 이유 · 항상 적용 (Claude가 정리)
          ├ 등록하기 → ④
          ├ 수정하기 → 고칠 내용을 받아 ③을 다시 보여 줌
          └ 취소하기 → 등록하지 않고 작업을 이어감
                                 ▼
④ 등록 완료   ✓ 결정 사항을 등록했어요. + 알린 사람 → 하던 작업을 이어감
```

- **결정**: T1은 두 경우로 시작해요. Claude가 알아챈 경우는 ①부터, 사람이 직접 바꾸려는 경우는 ②부터예요.
- **결정**: ①은 확인 절차예요. "이걸 등록할까요?"에 예 / 아니요로 답해요.
- **결정**: ②에서는 조사 결과를 보여 줘요. 충돌이 없으면 바로 ③으로 가고, 충돌이 있으면 "이대로 바꿀까요?"를 한 번 더 물어요.
- **결정**: "충돌"은 두 가지를 다 말해요. (가) 같은 것을 정한 결정 사항이 이미 있는 경우, (나) 다른 결정 사항과 서로 어긋나는 경우예요.
- **결정**: ③의 내용은 Claude가 알아서 정리해 넣어요. 사람은 등록하기 / 수정하기 / 취소하기 중에서 골라요.
- **결정**: 등록하면 등록됐다는 상태 메시지(④)가 떠요. 앱 링크는 넣지 않아요(5-5).
- **결정**: 항상 적용 여부는 Claude가 정하고, 틀리면 사람이 수정하기로 고쳐요. ③에서 항상 적용 줄을 강조해요.
- **제안**: 아니요·취소하기는 "이번 작업에서만 쓰고 결정 사항은 그대로 둔다"는 뜻이에요("[Spec] 담당자에게 알리기" 흐름도 "저장하지 않음, 이 작업 안에서만 사용").
- **제안**: 예로 저장할 때 출처는 "AI 대화", 바꾼 사람은 지금 대화하는 사람이에요(SIL-66). 바꾼 사람이 있어야 본인에게 알림이 가지 않아요(SIL-67).

## 3. 결정한 모양

예시는 착수 문서 데모 예시예요. 부건이 알림 제목 길이를 40자 이하에서 32자 이하로 바꾸고, 연결된 이슈는 #5(민수)와 #7(신지)이에요. `**`는 굵게예요. 화면에는 기호 없이 보여요. `☐ 결정 사항 등록`은 Claude Code 선택 화면 맨 위의 이름표(칩)예요.

### 3-1. ① 확인 (Claude가 알아챘을 때만)

```
● 이번 작업에서 정한 값이 있어요.
  앱 알림 제목을 공백 포함 32자 이하로 자르기

☐ 결정 사항 등록
이걸 결정 사항으로 등록할까요?
❯ 1. 예
     관련 결정 사항을 찾아보고 등록할 모습을 보여 드려요
  2. 아니요
     이번 작업에서만 쓰고 결정 사항으로 남기지 않아요
  3. Type something.
  4. Chat about this
```

"Type something.", "Chat about this"는 Claude Code가 자동으로 붙여요. 우리가 뺄 수 없어요(T3 결정기록 8장 16번).

### 3-2. ② 조사 결과

사람이 직접 바꾸려는 경우는 이렇게 시작해요.

```
> 앱 알림 제목 결정 사항을 32자로 바꿔 줘. Windows 알림 창에서 잘려.
```

**충돌 없음.** 문장 두 줄 뒤에 바로 ③이 이어져요.

```
● 관련 결정 사항을 찾아봤어요. 충돌하는 결정 사항이 없어요.
  아래처럼 새 결정 사항으로 등록할게요.
```

**충돌 있음.** (가)는 "바뀌는 결정 사항", (나)는 "어긋나는 결정 사항"으로 나눠요. 아래 (나)는 모양을 보여 주려고 만든 가상 예시예요.

```
● 관련 결정 사항을 찾아봤어요. 충돌하는 결정 사항이 2건 있어요.

  바뀌는 결정 사항
  [app] 앱 알림 제목은 40자 이하로 쓴다
    변경  공백 포함 40자 이하 ⭢ 공백 포함 32자 이하

  어긋나는 결정 사항
  [notify] 앱 알림 제목에는 결정 사항 제목을 그대로 쓴다
    이유  결정 사항 제목은 최대 40자라 32자를 넘을 수 있어요

☐ 결정 사항 등록
이대로 바꿀까요?
❯ 1. 예
     등록할 모습을 보여 드려요
  2. 아니요
     등록하지 않고 하던 작업을 이어가요
```

- (가)만 있으면 "어긋나는 결정 사항" 묶음을, (나)만 있으면 "바뀌는 결정 사항" 묶음을 빼요.
- (나)는 왜 어긋나는지 한 줄만 보여 주고 함께 고치지 않아요(4장 1번).
- 바뀌는 결정 사항의 `변경` 줄은 T2~T5 상세 화면과 같은 모양이에요. 그래서 착수 문서 T1의 "지금 값 / 바꿀 값"이라는 말을 쓰지 않아요. T3의 "지금 값"과 뜻이 반대라 헷갈리던 문제(질문 문서 경하-3)가 없어져요.

### 3-3. ③ 등록될 모습

```
● 아래처럼 등록할게요.

  [app] 앱 알림 제목은 32자 이하로 쓴다                    v1 ⭢ v2
    값    공백 포함 32자 이하
    이유  Windows 알림 창에서 32자를 넘으면 제목 끝이 잘림

  **항상 적용  아니오**   필요한 작업에서만 찾아 읽어요

☐ 결정 사항 등록
등록할까요?
❯ 1. 등록하기
     저장하고 연결된 이슈 담당자에게 알려요
  2. 수정하기
     고칠 내용을 말해 주세요 (예: 항상 적용으로 바꿔 줘)
  3. 취소하기
     등록하지 않고 하던 작업을 이어가요
```

| 경우           | 달라지는 줄                                                             |
| -------------- | ----------------------------------------------------------------------- |
| 항상 적용이 예 | `**항상 적용  예**   Claude Code를 켤 때 모든 작업에 들어가요 (9/10개)` |
| 새 결정 사항   | 제목 줄 끝의 `v1 ⭢ v2` 대신 `새 결정 사항`                              |
| 이유를 모름    | ③ 앞에서 `● 바꾸는 이유를 한 줄로 알려 주세요.`를 먼저 물어요(4장 4번)  |

- **결정**: 항상 적용 줄은 예든 아니오든 늘 보여 줘요. 다른 줄과 빈 줄로 떼고 굵게 해요. 아니오일 때 줄을 빼면 틀려도 고칠 수 없어서예요.
- **제안**: 항상 적용 뒤에 뜻을 짧게 붙여요. 예일 때는 지금 개수(9/10개)도 보여 줘요. 10개를 넘으면 등록할 수 없어서예요(`wiki.always-on.max-ten`).
- **제안**: 수정하기의 설명 줄에 "항상 적용으로 바꿔 줘"를 예로 넣어요. 이 값도 고칠 수 있다는 걸 알아채게 하려는 거예요.
- **제안**: 제목도 새 값에 맞게 고쳐요(40자 → 32자). 값만 고치고 제목을 그대로 두면 상세 화면에서 새 내용이 안 보여요(질문 문서 경하-4).
- ③은 Claude가 그리는 화면이라 색은 넣을 수 없고 굵게까지만 돼요.

### 3-4. ④ 등록 완료

```
⎿ ✓ 결정 사항을 등록했어요.
   [app] 앱 알림 제목은 32자 이하로 쓴다  v2 · 항상 적용 아니오
   연결된 이슈 2개의 담당자에게 확인할 변경을 보냈어요.

● 하던 작업을 이어갈게요.
```

| 경우                   | 달라지는 줄                                              |
| ---------------------- | -------------------------------------------------------- |
| 새 결정 사항           | `v2` 대신 `새 결정 사항`                                 |
| 연결된 이슈가 없음     | `연결된 이슈가 없어서 알림을 받는 사람은 없어요.`        |
| ①·② 아니요, ③ 취소하기 | `● 등록하지 않았어요. 하던 작업을 이어갈게요.` (한 줄만) |

- **결정**: 앱 링크("처리 상황은 앱에서 볼 수 있어요")는 넣지 않아요(5-5).
- **제안**: 첫 줄은 T3의 `✓ 기록했어요`와 같은 모양으로 맞췄어요.
- **제안**: ④는 저장 직후 hooks가 띄우면 좋겠어요(`save_standard` 뒤). 그러면 버전과 알린 이슈 수가 정확하게 나와요. Claude가 옮겨 쓰게 하면 줄이거나 빠뜨릴 수 있어요(흐름 결정기록 5-3과 같은 문제).

## 4. 예외 케이스 (미정: 넣을지 정해야 해요)

위키와 Linear 문서의 규칙을 T1 흐름에 대 보고 찾았어요. 3·4·7은 빠지면 틀린 결정 사항이 다른 사람에게 알려질 수 있어 꼭 넣기를 추천해요.

| #   | 경우                                      | 추천 처리                                                                                                          | 근거                                                               |
| --- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| 1   | (나) 어긋나는 결정 사항이 있음            | 한 번에 하나만 등록해요. ②에서 보여만 주고, 등록이 끝난 뒤 "어긋나는 결정 사항도 바꿀까요?"로 하나씩 이어서 물어요 | `detect.judge.one-per-run`, 킥오프 회의록 "한 번에 기준 하나씩"    |
| 2   | (가) 같은 것을 정한 결정 사항이 2개 이상  | 어느 것을 바꿀지 사람이 골라요                                                                                     | 위와 같음                                                          |
| 3   | 조사가 실패함 (서버 연결 안 됨 등)        | "충돌 없음"으로 보이면 안 돼요. "찾지 못했어요"를 따로 알리고 등록을 멈춰요                                        | `notify.error.not-empty`                                           |
| 4   | 이유를 모름                               | 이유는 지어내지 않아요. 대화에 없으면 ③ 앞에서 한 줄 물어요                                                        | 서버가 빈 이유를 거절함("지어내지 말고 사람에게 물어본 뒤")        |
| 5   | 되돌림 (새 값이 예전 버전 값과 같음)      | ③에 "v1 값으로 되돌려요"를 표시해요                                                                                | `detect.change.revert-mark`                                        |
| 6   | 하루에 두 번 넘게 바뀜                    | ②에서 "오늘 이미 2번 바뀌었어요"를 알리고 한 번 더 확인해요                                                        | `detect.safety.repeat-limit`                                       |
| 7   | 그 사이 다른 사람이 먼저 바꿈             | 저장하지 않고 새 내용으로 ②를 다시 보여 줘요                                                                       | `detect.conflict.hold`, `save_standard`의 기준 버전(`baseVersion`) |
| 8   | 새 결정 사항인데 맞는 영역이 없음         | 영역을 새로 만들지 않고 사람에게 어느 영역인지 물어요                                                              | `detect.change.no-new-area`                                        |
| 9   | 새 결정 사항이라 연결된 이슈가 없음       | 알림 받을 사람이 0명이에요. ④에 그대로 알릴지, 지금 작업 이슈에 연결할지 정해야 해요                               | 기준 모으기 스펙 "새 기준 v1로 저장, 지금 작업에 연결"             |
| 10  | 글자 수가 넘침 (제목 40자, 값·이유 120자) | Claude가 정리할 때 길이를 맞추고, 넘으면 ③에서 수정하기로 고쳐요                                                   | 착수 문서 5장 데이터 길이                                          |
| 11  | ①에서 아니요를 고른 뒤 같은 값이 또 나옴  | 같은 세션에서는 다시 묻지 않아요                                                                                   | 제안 (근거 없음)                                                   |
| 12  | 사람이 "이 결정 사항 없애 줘"라고 함      | 폐기도 T1에서 받을지, 이번 범위에서 뺄지 정해야 해요                                                               | `wiki.standard.no-delete`                                          |
| 13  | 항상 적용을 예로 등록하려는데 이미 10개   | 등록을 멈추고 "항상 적용이 10개라 더 넣을 수 없어요"를 알려요. 아니오로 바꾸거나 다른 것을 빼야 해요               | `wiki.always-on.max-ten`, 기준-작성-원칙 6장                       |

## 5. 이렇게 정한 이유

### 5-1. 두 경우를 한 흐름으로 (결정, 새 제안)

착수 문서 T1은 Claude가 먼저 묻는 경우만 다뤄요. 하지만 사람이 직접 결정 사항을 바꾸고 싶을 때도 같은 확인(조사 결과, 등록될 모습)이 필요해요. 그래서 두 경우가 ②에서 만나게 했어요. 사람이 직접 바꾸는 경우는 이미 마음먹은 것이라 ① 확인을 건너뛰어요.

### 5-2. 이유 한 줄 입력 대신 조사 결과와 등록될 모습 (결정)

착수 문서 T1은 "예/아니오를 고르고, 예라면 이유를 한 줄 입력"이에요. 그대로 하면 무엇과 부딪히는지 모른 채 등록하게 돼요. 그래서 예 다음에 조사 결과(②)를 보여 주고, 이유를 포함한 내용은 Claude가 정리해 등록될 모습(③)으로 보여 줘요. 이유를 대화에서 찾을 수 없을 때만 따로 물어요(4장 4번).

### 5-3. "충돌"은 두 가지 (결정)

같은 것을 정한 결정 사항이 있으면 그 결정 사항의 새 버전이 돼요(가). 다른 결정 사항과 어긋나는 경우(나)는 그대로 등록하면 위키 안에서 서로 다른 말을 하게 돼요. 둘 다 등록하기 전에 알아야 해서 ②에서 함께 보여 줘요.

### 5-4. 항상 적용은 Claude가 정하고 사람이 고친다 (결정)

`save_standard`는 항상 적용을 꼭 받아야 해요(SIL-73). 매번 사람에게 물으면 단계가 늘어요. 그래서 Claude가 정하고, 틀리면 사람이 수정하기로 고치게 했어요. 항상 적용이 예인 결정 사항은 Claude Code를 켤 때 모든 사람의 작업에 들어가니(6장), 틀린 채로 지나가지 않게 줄을 따로 떼어 굵게 보여 줘요.

### 5-5. 앱 링크는 뺀다 (결정)

처음에는 ④에 "처리 상황은 앱에서 볼 수 있어요" 링크를 넣으려 했어요. 하지만 지금 앱 화면은 받는 사람용 "나에게 온 변경"과 "답하기"뿐이에요(위키 `app.screen.inbox-first`, 착수 문서 A1~A4). 바꾼 본인에게는 확인할 변경이 생기지 않아서(SIL-67), 링크를 누르면 빈 화면이 보여요. 링크를 넣으려면 앱 화면과 팀 기준을 바꿔야 해서 이번에는 뺐어요.

### 5-6. 띄우는 방식은 가정 (미정)

어느 문서에도 T1을 띄우는 방식이 없어요. 근거는 도그푸딩 가이드의 "v0는 CLAUDE.md 규칙, 진짜 제품은 MCP 도구"뿐이에요. 그래서 "Claude가 안내문대로 묻고 선택 화면을 띄운다"고 가정하고 그렸어요. 정민님 서버가 이미 안내문으로 항상 적용 기준을 넘겨주고 있어서(실행 화면 6-3) 같은 방법을 쓸 수 있어요. MCP 입력 창(elicitation)은 T3에서 시험했다가 버렸어요(T3 결정기록 8장 15번).

## 6. "지속되는 제약 조건" 조사

예전 Figma 목업(Akasha, `docs/images/cli-test/mockup-1.png`)에는 결정의 종류가 둘이었어요.

| 종류                      | 예                                                             | 어디에 적용되나                                                                               |
| ------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 지속되는 제약 조건 (RULE) | `RULE-PAYMENT-AMOUNT-SERVER` "결제 금액은 서버에서만 계산한다" | 모든 작업. 목업 문구 "제약 조건은 모든 작업에 전달돼요", "다음 세션에도 작업 맥락에 들어가요" |
| 사양 변경 (SPEC)          | `SPEC-ORDER-DELIVERY-STATUS` 배송 상태 2단계                   | 연결된 작업만                                                                                 |

지금은 이 구분이 **"항상 적용" 칸 하나**로 바뀌었어요.

- 용어집(`team-wiki/용어.md`)에서 "지속되는 제약 조건"은 쓰지 않는 말이에요. "항상 적용되는 기준"(`always_on`)이라고 불러요. 화면 배지는 이미 뺐어요(질문 문서 0장).
- 항상 적용이 예이면 Claude Code를 켤 때 모든 사람의 작업 맥락에 자동으로 들어가요. 정민님 서버에서 9개가 들어오는 걸 확인했어요(`docs/기능-테스트.md` 5-1). 아니오이면 필요할 때 찾아 읽어요.
- 위키 전체에서 10개까지예요(`wiki.always-on.max-ten`, 기준-작성-원칙 6장).
- `save_standard`가 꼭 받아야 하는 5개(ID, 제목, 값, 이유, 항상 적용) 중 하나예요(SIL-73, `wiki.standard.required-fields` v2).
- 예전 시험에서는 이 구분이 흐릿해서 Claude가 제약 조건 건에도 "다시 열까요?"를 물었어요(`docs/CLI-동작-시험.md` "안내문은 빈틈 없이").

T1에 생긴 일: ③에 항상 적용 줄이 들어가고(5-4), 10개를 넘는 예외(4장 13번)가 생겼어요. 항상 적용 결정 사항이 바뀌면 누구에게 알릴지는 비어 있어요(9장).

## 8. 버린 시안과 이유

| 순서 | 시안                                                                                    | 버린 이유                                                                                                                                       |
| ---- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 띄우는 방식을 먼저 골라 그리기 (A 선택 화면 / B 저장 직전 권한 확인 창 / C MCP 입력 창) | 부건이 문서를 더 찾아본 뒤 두 경우의 흐름부터 정하기로 했어요. 방식은 가정으로 두고 경하님께 물어요(5-6)                                        |
| 2    | 아니오 설명 "결정 사항대로 40자 이하로 만들어요"                                        | 뜻을 반대로 썼어요. 질문이 "결정 사항**도** 바꿀까요?"이고 스펙 흐름도도 "이 작업 안에서만 사용"이라, 아니오는 결정 사항을 그대로 두는 뜻이에요 |
| 3    | 두 경우를 서로 다른 질문으로 나누기 (경우 2는 "이대로 저장할까요? 저장 / 고치기")       | 부건이 ①을 확인 절차로, ②를 조사 결과로 보고 두 경우를 한 흐름으로 이었어요(5-1)                                                                |
| 4    | 경우 2는 확인 없이 저장하고 결과만 보여 주기                                            | 값이 틀려도 다른 사람에게 알림이 바로 가요                                                                                                      |
| 5    | ②에서 "어떻게 바꿀까요?"로 바꿀 값과 이유를 묻기 (한 번에 / 차례로 / 초안 고르기)       | 부건이 ②는 묻는 곳이 아니라 조사 결과를 보여 주는 곳으로 정했어요. 내용은 Claude가 정리해요                                                     |
| 6    | 항상 적용이 아니오면 줄을 빼서 화면을 짧게 (Claude 추천)                                | 안 보이면 틀려도 고칠 수 없어요. 늘 보여 주고 강조하기로 했어요(5-4)                                                                            |
| 7    | ④에 "처리 상황은 앱에서 볼 수 있어요" + 앱 링크                                         | 바꾼 사람이 볼 앱 화면이 없어요. 넣으려면 팀 기준을 바꿔야 해서 뺐어요(5-5)                                                                     |
