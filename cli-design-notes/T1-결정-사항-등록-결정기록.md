## 1. 이 화면이 하려는 일 (의도)

| 의도                                     | 어떻게 지키나                                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **결정 사항이 조용히 달라지지 않는다**   | 작업 중에 결정 사항과 다른 값을 쓰게 되면 Claude가 먼저 "이걸 등록할까요?"를 물어요(위키 `work.wiki.ask-before-change`, SIL-66) |
| **사람이 직접 바꿀 때도 같은 길로 간다** | 사람이 "결정 사항 바꿔 줘"라고 하면 확인 단계를 건너뛰고 조사 결과부터 보여 줘요                                                |
| **무엇과 부딪히는지 알고 등록한다**      | 등록하기 전에 관련 결정 사항을 찾아 보여 줘요. 같은 것을 정한 결정 사항과 어긋나는 결정 사항을 나눠 보여 줘요                   |
| **사람은 고르고 고치기만 한다**          | 제목·값·이유·항상 적용은 Claude가 정리해 넣어요. 사람은 등록될 모습을 보고 등록하기 / 수정하기 / 취소하기 중에서 골라요         |
| **모든 작업에 들어가는 값은 꼭 본다**    | 항상 적용 여부는 Claude가 정하되, 예든 아니오든 따로 한 줄로 굵게 보여 줘서 틀리면 바로 고치게 해요                             |
| **등록했는지 확실히 안다**               | 저장한 뒤 `✓ 결정 사항을 등록했어요.`와 누구에게 알렸는지를 보여 줘요                                                           |

## 2. 결정한 흐름 (10/12 오후 고침: ①② 합침)

```
[경우 1] Claude가 작업 중에 알아챔          [경우 2] 사람이 "결정 사항 바꿔 줘"
          │                                            │
          ▼                                            ▼
①② 다른 결정 사항 확인   Claude가 관련 결정 사항을 찾아 목록을 띄움 (hooks)
          경우 1: "그래도 진행할까요?"                 경우 2: 묻지 않음
            ├ 아니요 → 작업을 하지 않고 끝냄 (10/13)          │
            └ 예 ──────────────────────┐                    │
                                       ▼                    ▼
   (사람이 한 말에 이유가 없을 때만) "이 결정 사항을 바꾸는 이유를 작성해 주세요." → 입력 → 정리
                                       ▼
③ 등록될 모습   제목 · 값 · 이유 · 항상 적용 · 알림 받을 이슈 표 (hooks)
          ├ 등록하기 → ④
          ├ 수정하기 → 고칠 내용을 받아 ③을 다시 보여 줌
          └ 취소하기 → 등록을 취소함. 하던 작업은 멈추고 사람의 말을 기다림 (10/13)
          (첫 질문·③을 Esc로 닫아도 같음, 10/14)
                                       ▼
④ 등록 완료   ✓ 결정 사항을 등록했어요. + 알린 사람 (hooks) → 하던 작업을 이어감
```

- **결정**: T1은 두 경우로 시작해요. Claude가 작업 중에 알아챈 경우(경우 1)와 사람이 직접 바꾸려는 경우(경우 2)예요.
- **결정**: 확인(①)과 조사 결과(②)를 **한 단계로 합쳐요**(10/12, 시안 확인 뒤). "부탁하신 작업이 기존 결정 사항과 달라요" → 다른 결정 사항 목록 → "기존 결정 사항과 다른 작업이에요. 그래도 진행할까요?" 순서예요(10/13 말 바꿈, 3-1).
- **결정**: 경우 2는 충돌 표만 보여 주고 묻지 않고 ③으로 가요. 이미 바꾸겠다고 말했기 때문이에요. 그만둘 기회는 ③의 취소하기예요(10/12).
- **결정**: 경우 2에서 다른 결정 사항이 있으면 ③의 질문을 `달라지게 되는 기존 결정 사항 내역을 확인했나요? 이대로 등록할까요?`로 바꿔요(10/13). 목록 바로 뒤에 ③이 떠서 읽기 전에 지나가 버렸어요(아티팩트 시안). 묻는 횟수는 늘리지 않고 질문으로 다시 보게 해요. 경우 1은 목록을 보고 이미 답해서, 다른 결정 사항이 없으면 확인할 게 없어서 `등록할까요?` 그대로예요.
- **결정**: 충돌 화면과 ③ 등록될 모습은 **hooks가 직접 띄워요(B)**. Claude는 내용만 도구(`show_conflicts`, `preview_standard`)에 넘겨요(10/12, 5-6).
- **결정**: 구분은 두 가지예요. **변경**(같은 것을 다르게 정함)과 **어긋남**(같이 지킬 수 없음)이에요. "변경"은 받는 사람 화면(T2~T5 v2)의 태그 `(변경)`과 맞췄어요(10/13, 처음 이름은 "바뀜"). 잠금은 구분에 넣지 않아요(10/13, 8장 28번).
- **결정**: ③의 내용은 Claude가 정리해 넣어요. 사람은 등록하기 / 수정하기 / 취소하기 중에서 골라요.
- **결정**: 등록하면 등록됐다는 상태 메시지(④)가 떠요. 앱 링크는 넣지 않아요(5-5).
- **결정**: 항상 적용 여부는 Claude가 정하고, 틀리면 사람이 수정하기로 고쳐요. ③에서 항상 적용 줄을 따로 떼어 보여 주고, 예일 때 굵게 해요(3-3).
- **결정**: 경우 1의 질문은 `기존 결정 사항과 다른 작업이에요. 그래도 진행할까요?`예요. **예**는 결정 사항을 바꾸고 진행(③으로), **아니요**는 부탁받은 작업을 하지 않고 끝내요. 코드도 결정 사항도 그대로예요(10/13, 부건. 8장 38번). 새 값을 이번 작업에만 쓰는 길은 없어요. "[Spec] 담당자에게 알리기" 흐름도의 "저장하지 않음, 이 작업 안에서만 사용"과 달라져서 7장에 적었어요.
- **결정**: 취소하기는 **이 결정 사항 등록을 취소**하는 거예요. 결정 사항은 그대로예요. 하던 작업이 있으면 코드를 고치지 않고 멈춘 채 사람의 말을 기다리고, 그 말대로 다음을 해요(10/13, 부건. 8장 37번). 아니요와 달리 새 값을 코드에 쓰지 않아요.
- **결정**: 선택 창(첫 질문, ③)을 Esc로 닫으면 **취소하기와 같게** 처리해요(10/14, 부건. SIL-66 PR #22 확인 요청). 아니요가 아니라 취소하기예요. 코드를 고치지 않고 멈춘 채 사람의 말을 기다려요. Esc를 누른 바로 그때는 Claude Code가 요청을 멈춰서 `User declined to answer questions` 줄만 남고(테스트 A9·A10), 사람이 다음에 말하면 그 말에 답하기 전에 3-4의 취소 문구를 먼저 보여 줘요. 다음 말이 "계속해 줘"처럼 분명하지 않으면 작업하지 않고 기다리고, 결정 사항을 바꾸라는 말이면 T1을 처음부터 다시 해요(경하님 PR #22 구현).
- **결정**: hooks가 띄우는 모든 글(①② · ③ · ④) 맨 위에 Claude Code가 `PostToolUse:도구 이름 says:` 머리글을 붙여요. 바꿀 수 없다고 경하님이 확인해서 **그대로 둬요**(10/14, 부건. SIL-66 PR #24 확인 요청). 3-1·3-3·3-4 그림의 첫 줄이 이 머리글이에요. 도구 이름은 구현에 따라 달라요. 경하님 구현은 명령(Bash)으로 ③을 띄워서 `PostToolUse:Bash says:`, 시안(`prototype/t1-prototype/`)은 MCP 도구라 `PostToolUse:mcp__wiki__preview_standard says:`예요. 머리글은 글 위의 별도 한 줄이라 칸 수(76칸)에는 넣지 않고, 화면은 한 줄 늘어요.
- **제안**: 예로 저장할 때 출처는 "AI 대화", 바꾼 사람은 지금 대화하는 사람이에요(SIL-66). 바꾼 사람이 있어야 본인에게 알림이 가지 않아요(SIL-67).

## 3. 결정한 모양

예시는 착수 문서 데모 예시예요. 부건이 알림 제목 길이를 40자 이하에서 32자 이하로 바꾸고, 연결된 이슈는 #5(민수)와 #7(신지)이에요. `**`는 굵게예요. 화면에는 기호 없이 보여요. `☐ 결정 사항 등록`은 Claude Code 선택 화면 맨 위의 이름표(칩)예요.

### 3-1. ①② 다른 결정 사항 확인 (한 단계, hooks가 띄움)

`⎿` 아래는 hooks가 띄우는 글이에요. 맨 윗줄은 Claude Code가 붙이는 머리글이고(2장, 10/14), 그 아래가 우리가 그리는 글이에요. 머리표는 노란 막대(노랑을 반전한 칸 하나) + 노란 글자예요. 위아래 선은 없어요. 결정 사항 제목은 터미널 기본 글자색 굵게예요. 예시의 `▌`가 막대예요. 시안 `prototype/t1-prototype/proto/screens.py`가 실제로 만든 글을 옮겼어요(10/13).

```
⎿ PostToolUse:mcp__wiki__show_conflicts says:
  ▌ 부탁하신 작업이 기존 결정 사항과 달라요
    작업  알림 제목을 32자에서 자르기

    변경    [app] 앱 알림 제목은 40자 이하로 쓴다
            40자 이하로 정한 길이를 32자 이하로 다시 정해요
    어긋남  [notify] 앱 알림 제목에는 결정 사항 제목을 그대로 쓴다
            결정 사항 제목(최대 40자)을 그대로 쓰면 32자에서 잘려요

☐ 결정 사항 등록
기존 결정 사항과 다른 작업이에요. 그래도 진행할까요?
❯ 1. 예
     결정 사항을 등록하고 작업을 진행할게요. 등록될 모습 먼저 보여 드릴게요
  2. 아니요
     부탁하신 작업은 멈춰 둘게요. 기존 결정 사항은 그대로 유지할게요
```

| 경우                         | 달라지는 것                                                                                                                                                                                |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 경우 2 (사람이 직접)         | 머리표 `요청하신 변경이 기존 결정 사항과 달라요`, 둘째 줄 `요청  {요청}`. 질문 없이 ③으로 가고, ③의 질문이 `달라지게 되는 기존 결정 사항 내역을 확인했나요? 이대로 등록할까요?`예요(10/13) |
| 경우 2 · 다른 결정 사항 없음 | 요청 줄 없이 **녹색 막대 + 녹색 글자 한 줄** `▌ 요청하신 변경과 다른 결정 사항이 없어요`(터미널 기본 16색 초록 32). 바로 ③(10/13, 부건)                                                    |

- **결정**: 화면에서 "충돌"이라는 말을 쓰지 않아요. 위키 용어집과 `detect.conflict.hold`에서 "충돌"은 같은 버전을 두 사람이 동시에 바꾼 상황(`conflict`)이에요. 위키가 이 상황을 부르는 말(`work.wiki.ask-before-change` "위키와 다르게 만들게 되면")을 따라 **"달라요", "다른 결정 사항"**이라고 써요(10/13, 부건. 신지님과 확정 필요). 이 문서의 다른 장에 남은 "충돌"은 10/13 전 기록이에요.
- **결정**: 다른 결정 사항마다 **구분 · `[영역] 제목`**을 한 줄에, 그 아래에 **왜 그렇게 판단했는지** 한 문장을 써요. 결정 사항 ID는 보여 주지 않아요. 사람에게 중요한 건 "어떤 결정 사항이고, 왜 다르다고 봤는지"예요(10/13, 부건. 8장 26번).
- **결정**: 이 화면은 위아래 선을 쓰지 않아요. 머리표 앞에 그 색의 막대(색을 반전한 칸 하나 + 빈칸)를 둬요. T2~T5 상태 줄의 노란 막대와 같은 모양이에요(10/13, 부건. 8장 34번). ③ 등록될 모습은 위아래 선을 그대로 써요. 선은 어디서나 1칸인 `-`예요(상자 선 `─`는 한국어 코딩 글꼴에서 2칸, T2 본문 결정기록 3-7).
- **결정**: 다른 결정 사항이 있을 때 머리표는 **노란 글자**, 없을 때 한 줄은 **녹색 글자**예요. 터미널 기본 16색의 노랑(33)·초록(32)이라 어두운·밝은 테마 모두 터미널이 맞춰요(10/13, 부건. 처음엔 빨강 31).
- **결정**: T1의 위 선은 왼쪽 `--`를 꾸미지 않고(hooks 기본 회색), 머리표 글자를 굵게 하지 않아요. ③ 등록될 모습에 써요. 다른 결정 사항 확인은 선 없이 막대로 시작해요(10/13, 부건. 8장 31·34번).
- **결정**: 판단 이유는 한 문장이에요. 그 결정 사항의 무엇이 새 값과 맞지 않는지 드러나게 써요(10/12).
- 76칸 안에 맞춰요(Claude Code가 hooks 글 앞에 2칸을 들여 써서 78칸). 제목과 이유는 66칸에서 띄어쓰기 단위로 줄을 바꿔요.
- "Type something.", "Chat about this"는 Claude Code가 자동으로 붙여요. 우리가 뺄 수 없어요(T3 결정기록 8장 16번).

### 3-3. ③ 등록될 모습 (hooks가 띄움)

```
⎿ PostToolUse:mcp__wiki__preview_standard says:
  -- 결정 사항을 이렇게 등록할까요 -------------------------------------------
    [app] 앱 알림 제목은 32자 이하로 쓴다
      값    공백 포함 32자 이하
      이유  Windows 알림 창에서 32자를 넘으면 제목 끝이 잘림

      항상 적용  아니오

    ID   담당자  이슈
    #5   민수    담당자에게 알리고 답 기록하기
    #7   신지    앱 알림과 나에게 온 변경 화면
  ----------------------------------------------------------------------------

☐ 결정 사항 등록
```

| 예외 8          | 새 결정 사항인데 맞는 영역이 없음    | 따로 묻지 않아요. ③ 제목 줄의 `[영역]`을 보고 틀리면 수정하기로 고쳐요                                                                                    |

### 4-3. 충돌 구분은 두 가지

"구분"은 **변경**과 **어긋남** 두 가지만 써요(5-3). 10/13에 "바뀜"을 "변경"으로 바꿨어요.

| 구분   | 뜻                                                      | 여기에 넣는 것 (10/12 합침)                                                                                                   |
| ------ | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 변경   | 같은 것을 다르게 정함 → 그 결정 사항의 새 버전으로 등록 | 충돌 1, 충돌 5(되돌림)                                                                                                        |
| 어긋남 | 다른 결정 사항인데 같이 지킬 수 없음 → 보여만 줘요      | 충돌 2, 충돌 4(범위 겹침), 충돌 7(항상 적용과 부딪힘), 충돌 8(값에 기대는 결정 사항). 무엇 때문인지는 판단 이유 문장으로 써요 |

## 5. 이렇게 정한 이유

### 5-1. 두 경우를 한 흐름으로 (결정, 새 제안)

착수 문서 T1은 Claude가 먼저 묻는 경우만 다뤄요. 하지만 사람이 직접 결정 사항을 바꾸고 싶을 때도 같은 확인(조사 결과, 등록될 모습)이 필요해요. 그래서 두 경우가 ②에서 만나게 했어요. 사람이 직접 바꾸는 경우는 이미 마음먹은 것이라 ① 확인을 건너뛰어요.

### 5-2. 이유 한 줄 입력 대신 조사 결과와 등록될 모습 (결정)

착수 문서 T1은 "예/아니오를 고르고, 예라면 이유를 한 줄 입력"이에요. 그대로 하면 무엇과 부딪히는지 모른 채 등록하게 돼요. 그래서 예 다음에 조사 결과(②)를 보여 주고, 이유를 포함한 내용은 Claude가 정리해 등록될 모습(③)으로 보여 줘요. 이유는 사람이 한 말에 있으면 Claude가 정리해 넣고, 없을 때만 물어요(10/12, 4-2 예외 4). 처음에는 작업 내용과 기존 결정 사항에서도 유추하게 했는데, 시안에서 사람이 하지 않은 이유를 지어냈어요(테스트 A8).

### 5-3. "충돌"은 두 가지 (결정)

같은 것을 정한 결정 사항이 있으면 그 결정 사항의 새 버전이 돼요(가). 다른 결정 사항과 어긋나는 경우(나)는 그대로 등록하면 위키 안에서 서로 다른 말을 하게 돼요. 둘 다 등록하기 전에 알아야 해서 ②에서 함께 보여 줘요.

### 5-4. 항상 적용은 Claude가 정하고 사람이 고친다 (결정)

`save_standard`는 항상 적용을 꼭 받아야 해요(SIL-73). 매번 사람에게 물으면 단계가 늘어요. 그래서 Claude가 정하고, 틀리면 사람이 수정하기로 고치게 했어요. 항상 적용이 예인 결정 사항은 Claude Code를 켤 때 모든 사람의 작업에 들어가니(6장), 틀린 채로 지나가지 않게 줄을 따로 떼어 보여 주고, 예일 때는 굵게 해요(10/13).

### 5-5. 앱 링크는 뺀다 (결정)

처음에는 ④에 "처리 상황은 앱에서 볼 수 있어요" 링크를 넣으려 했어요. 하지만 지금 앱 화면은 받는 사람용 "나에게 온 변경"과 "답하기"뿐이에요(위키 `app.screen.inbox-first`, 착수 문서 A1~A4). 바꾼 본인에게는 확인할 변경이 생기지 않아서(SIL-67), 링크를 누르면 빈 화면이 보여요. 링크를 넣으려면 앱 화면과 팀 결정 사항을 바꿔야 해서 이번에는 뺐어요.

### 5-6. 띄우는 방식: Claude는 묻고, 화면은 hooks가 띄운다 (결정, 10/12)

어느 문서에도 T1을 띄우는 방식이 없어요. 근거는 도그푸딩 가이드의 "v0는 CLAUDE.md 규칙, 진짜 제품은 MCP 도구"뿐이에요.

- 처음에는 "Claude가 안내문대로 그린다(A-1)"로 시안을 만들었어요. 실제로 돌려 보니 Claude가 틀 대신 자기 말로 요약했어요("충돌하는 항목 2건을 찾았어요. 하나는 …"). ③은 카드를 띄우지 않고 "정리해서 보여드렸어요"라고만 했어요. T2~T5에서 겪은 문제와 같아요(흐름 결정기록 8장 8번).
- 그래서 T2~T5처럼 **화면 글은 hooks가 띄우고, Claude는 내용만 도구에 넘기고 선택 화면만 띄우게** 바꿨어요(B). 도구는 `show_conflicts`(충돌 목록)와 `preview_standard`(등록할 제목·값·이유·항상 적용)예요. 버전과 알림 받을 이슈는 서버가 채워요.
- 선택 화면은 그대로 Claude가 AskUserQuestion으로 띄워요. hooks는 키 입력을 받을 수 없어요(흐름 결정기록 6장 테스트 C). MCP 입력 창(elicitation)은 T3에서 시험했다가 버렸어요(T3 결정기록 8장 15번).
- 실제 제품에서는 두 도구를 누가 만들지 정해야 해요(9장 경하님 질문).

## 6. "지속되는 제약 조건" 조사

예전 Figma 목업(Akasha, `docs/images/cli-test/mockup-1.png`)에는 결정의 종류가 둘이었어요.

| 종류                      | 예                                                             | 어디에 적용되나                                                                               |
| ------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 지속되는 제약 조건 (RULE) | `RULE-PAYMENT-AMOUNT-SERVER` "결제 금액은 서버에서만 계산한다" | 모든 작업. 목업 문구 "제약 조건은 모든 작업에 전달돼요", "다음 세션에도 작업 맥락에 들어가요" |
| 사양 변경 (SPEC)          | `SPEC-ORDER-DELIVERY-STATUS` 배송 상태 2단계                   | 연결된 작업만                                                                                 |

지금은 이 구분이 **"항상 적용" 칸 하나**로 바뀌었어요.

- 용어집(`team-wiki/용어.md`)에서 "지속되는 제약 조건"은 쓰지 않는 말이에요. "항상 적용되는 결정 사항"(`always_on`)이라고 불러요. 화면 배지는 이미 뺐어요(질문 문서 0장).
- 항상 적용이 예이면 Claude Code를 켤 때 모든 사람의 작업 맥락에 자동으로 들어가요. 정민님 서버에서 9개가 들어오는 걸 확인했어요(`docs/기능-테스트.md` 5-1). 아니오이면 필요할 때 찾아 읽어요.
- 위키 전체에서 10개까지예요(`wiki.always-on.max-ten`, 기준-작성-원칙 6장).
- `save_standard`가 꼭 받아야 하는 5개(ID, 제목, 값, 이유, 항상 적용) 중 하나예요(SIL-73, `wiki.standard.required-fields` v2).
- 예전 시험에서는 이 구분이 흐릿해서 Claude가 제약 조건 건에도 "다시 열까요?"를 물었어요(`docs/CLI-동작-시험.md` "안내문은 빈틈 없이").

T1에 생긴 일: ③에 항상 적용 줄이 들어가고(5-4), 10개를 넘는 예외(4-2 예외 13)가 생겼어요. 항상 적용 결정 사항이 바뀌면 누구에게 알릴지는 비어 있어요(9장).
