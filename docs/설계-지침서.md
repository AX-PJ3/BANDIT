# 이 도구 설계 지침서

> **누가 읽는 글인가요:** 디자이너와 팀원 모두가 읽어요. 개발 용어는 꼭 필요할 때만 쓰고, 처음 나올 때 괄호로 풀어 써요.
> **원본:** 팀 위키(`team-wiki/`)의 기준 90개예요. 이 글은 그 기준을 "어떻게 만들었는지"로 다시 묶은 거예요. 기준과 이 글이 다르면 기준이 맞아요.
> **기준일:** 2026-10-09 (10/12 팀 피드백 반영 D51, PR #7 규칙 반영 D53, 반영함 표시 D56, 화면 문구 "결정 사항" D57).
> **팀 저장소에 없는 것:** 이 글에 나오는 바뀐 기준 찾기 뼈대(`apps/detect`)와 GitHub Actions(`ci.yml`, `detect.yml`, `backup.yml`), `docs/main-ruleset.json`은 정민님 로컬에만 있어요. 바뀐 기준 찾기와 검사(CI)는 경하님 작업과 겹쳐서 따로 정해 올려요.
> **기능을 만드는 사람은** 부록 C(팀원 기능 연결 방법, SIL-61~67)를 먼저 읽어요. 5~8절은 지금 위키를, 부록 C는 착수 안내 v2를 따라요.
> **타입과 칸 이름은** [타입 명세](타입명세서.md)에 있어요. 착수 안내·코드·DB가 같은 것을 부르는 이름 연결표, 칸마다 뜻과 비어 있을 수 있는지가 들어 있어요.

## 1. 이 도구가 하는 일

이 도구는 **바뀐 기준을 몰라서 생기는 재작업을 줄여요** (goal.problem.rework).

팀원은 각자 AI(Claude Code)와 일해요. 누군가 팀 기준을 바꿔도 다른 사람의 AI는 예전 기준으로 계속 일해요. 그러면 나중에 결과물을 다시 만들어야 해요. 이 도구는 바뀐 기준을 찾아서, 그 기준과 이어진 일을 하는 사람에게만 알려요. 알림을 받은 사람은 두 가지만 답해요.

- 첫 사용자는 개발자와 디자이너가 각자 Claude Code로 일하는 팀이에요 (goal.user.first-team).
- 이번 범위는 팀 하나, 저장소 하나예요 (goal.scope.one-team).
- 성공은 "몰랐다"고 답한 변경의 수로 재요 (goal.metric.primary). 이 숫자가 문제가 실제로 있다는 증거예요.

## 2. 한눈에 보는 흐름

```
① 기준을 모아요          팀 위키 → 데이터베이스(DB). AI는 MCP 도구로 읽고 써요
        │
② 바뀐 기준을 찾아요      main에 반영된 PR을 보고 AI가 바뀐 기준을 찾아 새 버전으로 저장해요
        │
③ 영향받는 사람에게 알려요  바뀐 기준과 이어진 이슈의 담당자마다 "확인할 변경"을 하나씩 만들어요
        │                  터미널(Claude Code를 켤 때), 웹 앱(PWA) 알림으로 보내요
④ 담당자가 답해요         관계있다/관계없다 → (관계있다면) 알았다/몰랐다
        │
⑤ 숫자로 세요            "관계있다 N건 중 몰랐다 M건"
```

- **MCP 서버**: Claude Code가 켜질 때 함께 연결되는 작은 프로그램이에요. AI가 팀 위키를 읽고 쓰는 통로예요.
- **PR**: 코드 변경을 main에 합치자는 요청이에요. 바뀐 기준 찾기는 합쳐진 PR만 봐요 (detect.input.merged-pr-only).

## 3. 꼭 알아야 할 말

코드와 DB에서 쓰는 이름(예: 관계있다 → `affected`)은 [타입 명세 2절](타입명세서.md#2-같은-것을-부르는-이름)에 있어요.

| 우리가 쓰는 말      | 뜻                                                                               | 쓰지 않는 말                  |
| ------------------- | -------------------------------------------------------------------------------- | ----------------------------- |
| 기준                | 팀 위키의 규칙 하나예요. 값은 한 문장으로 끝나요                                 | 결정 사항, 스펙, RULE         |
| 기준 버전           | 기준이 바뀔 때마다 1씩 올라가는 번호예요. 이전 버전은 지우지 않아요              | -                             |
| 적용 범위           | 기준이 적용되는 코드 경로, API, 화면, 문서예요. 알림을 보낼 사람을 찾는 열쇠예요 | -                             |
| 항상 적용           | 모든 작업에서 지키는 기준이에요. 위키 전체에서 10개까지예요                      | 지속되는 제약 조건            |
| 잠금                | 사람이 잠근 기준은 AI가 고치지 못해요                                            | -                             |
| 폐기                | 더 쓰지 않는 기준이에요. 지우지 않고 표시만 해요                                 | 삭제                          |
| 이슈                | Linear의 할 일 하나예요                                                          | 태스크, 작업                  |
| 확인할 변경         | 담당자가 아직 확인하지 않은 바뀐 기준이에요. 이슈마다 하나씩 생겨요              | 확인 대기                     |
| 관계있다 / 관계없다 | 이 변경이 내 일에 영향을 주는지에 대한 답이에요. 기준을 승인하는 게 아니에요     | 수락 / 거절, 영향 있음 / 없음 |
| 알았다 / 몰랐다     | 관계있다고 답할 때 미리 알았는지에 대한 답이에요                                 | -                             |
| 충돌                | 같은 버전을 보고 두 사람이 서로 다르게 고친 상황이에요                           | -                             |
| 되돌리기            | 기준을 앞선 버전의 값으로 돌리는 거예요. 되돌린 것도 새 버전으로 남아요          | 원복, revert                  |
| 이 도구             | 서비스 이름을 정하기 전까지 쓰는 이름이에요                                      | 예전 가제                     |

## 4. 기준 하나의 모양

| 칸        | 쓰는 법                                                                                      | 저장할 때 검사              |
| --------- | -------------------------------------------------------------------------------------------- | --------------------------- |
| ID        | `영역.주제.규칙` 세 부분이에요. 영문 소문자, 숫자, 하이픈만 써요. 한 번 정하면 바꾸지 않아요 | 필수, 모양 검사             |
| 제목      | 누구나 읽을 수 있는 한 문장이에요. 40자 이하예요                                             | 필수 (40자 넘으면 경고)     |
| 값        | 정한 내용 한 문장이에요. 숫자, 이름, 조건으로 확인할 수 있게 써요                            | 필수                        |
| 이유      | 왜 이렇게 정했는지 한 문장이에요                                                             | 필수                        |
| 항상 적용 | 예 / 아니오. 버전마다 남고, 되돌리면 그 버전의 값으로 돌아가요                               | 필수                        |
| 적용 범위 | `코드:` / `API:` / `화면:` / `문서:` 중 하나 이상이에요                                      | 저장만 해요 (아래 6-1 참고) |
| 근거      | PRD 절, PR 번호, 회의 날짜, Figma 링크처럼 어디서 정했는지예요                               | 저장만 해요 (아래 6-1 참고) |
| 상태      | 사용 / 폐기. 폐기면 대체한 기준 ID를 적어요                                                  | -                           |
| 잠금      | 예면 AI가 고치지 못해요                                                                      | 사람만 바꿔요               |

- 값에 "그리고", "또한", "단,"이 들어가면 규칙이 두 개일 수 있어요. 저장은 되지만 경고가 나오고, AI는 기준을 나눌지 사람에게 물어요 (wiki.standard.one-rule).
- "적절히", "가능하면", "필요시"처럼 확인할 수 없는 말은 쓰지 않아요.

## 5. 저장소가 저절로 지키는 규칙

아래 규칙은 사람이나 AI가 실수해도 DB(데이터베이스)가 막아요. MCP, 바뀐 기준 찾기, 앱 어디서 저장해도 같아요.

**기준과 버전**

- 기준은 지울 수 없어요. 쓰지 않으면 폐기로 바꿔요 (wiki.standard.no-delete).
- 이전 버전은 고칠 수 없어요. 기준이 바뀌면 새 버전이 쌓여요 (wiki.version.append-only).
- 버전마다 값, 이유, 근거, 적용 범위, 바꾼 사람, 바꾼 시간, AI가 고쳤는지를 남겨요 (wiki.version.record-fields).
- 되돌리기도 새 버전이에요. 새 값이 앞선 버전의 값과 같아지면 되돌림으로 표시하고, 몇 버전으로 돌아갔는지 남겨요 (wiki.revert.new-version, detect.change.revert-mark).
- 같은 버전을 보고 두 사람이 고치면 늦게 저장한 쪽은 저장되지 않아요. 그 변경은 버리지 않고 **충돌로 보류**해요. 사람이 정할 때까지 담당자에게 알리지 않아요 (detect.conflict.hold).
- 잠긴 기준은 AI가 고칠 수 없어요 (wiki.lock.human-first).
- 항상 적용 기준은 10개를 넘을 수 없어요 (wiki.always-on.max-ten).
- 기준 ID는 정확히 세 부분이에요 (data.standard.id-format).

**AI 안전 규칙**

- AI는 새 영역을 만들지 못해요. 있는 영역 안에서만 기준을 만들고 고쳐요 (detect.change.no-new-area).
- PR에서 찾은 변경은 근거(PR 번호와 바뀐 줄)가 있어야 저장돼요 (detect.change.evidence).
- PR에서 찾은 변경은 같은 기준을 하루에 두 번 넘게 바꾸지 못해요. 그때는 사람에게 물어요 (detect.safety.repeat-limit).

**답과 기록**

- 답은 지우거나 고칠 수 없어요. 확인할 변경 하나에 답은 하나이고, 답 취소는 없어요 (10/12 피드백, D51).
- 확인할 변경도 지울 수 없어요. 지표의 재료라서 끝까지 남겨요.

**권한과 백업**

- 팀이 함께 쓰는 공용 키로는 읽기와 정해진 저장 통로만 쓸 수 있어요. 표에 직접 쓰거나 지울 수 없어요.
- 하루 한 번 표 전체를 백업해요. 저장소가 공개라서 백업 파일은 암호화해서 보관해요 (wiki.backup.daily).

## 6. 누가 무엇을 할 수 있나

| 일                       | 사람        | AI (Claude Code)               | 어디서                                          |
| ------------------------ | ----------- | ------------------------------ | ----------------------------------------------- |
| 기준 찾기, 읽기          | ✔           | ✔                              | `get_index`, `search_standards`, `get_standard` |
| 기준 새로 만들기, 고치기 | ✔           | ✔ (잠긴 기준, 새 영역은 못 함) | `save_standard`                                 |
| 되돌리기                 | ✔           | ✔                              | `revert`                                        |
| 폐기                     | ✔           | ✘ (사람에게 알려요)            | `pnpm sil deprecate`                            |
| 잠금 걸기와 풀기         | ✔           | ✘                              | 위키 파일 → `sil import`                        |
| 충돌 정리                | ✔           | ✘                              | `resolve_conflict`                              |
| 확인할 변경에 답하기     | 받은 사람만 | -                              | 터미널, 앱                                      |

- AI가 쓰는 위키 도구는 다섯 개예요: `get_index`, `search_standards`, `get_standard`, `save_standard`, `revert` (wiki.mcp.five-tools).
- AI는 관련 기준이 없으면 지어내지 않고 사람에게 물어요. 그 답을 새 기준으로 저장해요 (wiki.ask.when-missing).
- AI가 위키와 다른 결과물을 만들게 되면, 만들기 전에 "팀 기준을 바꾸는 것인지" 먼저 물어요 (work.wiki.ask-before-change).

### 6-1. 지금 위키와 다르게 동작하는 곳

- **필수 칸:** 위키 기준 wiki.standard.required-fields는 근거와 적용 범위도 필수라고 해요. 착수 안내 v2(SIL-65)는 필수 칸을 5개(ID, 제목, 값, 이유, 항상 적용)로 정했어요. 지금 DB는 5개만 검사해요. 대신 항상 적용 기준인 wiki.standard.required-fields가 세션마다 AI에게 들어가서, AI는 근거와 적용 범위가 비면 사람에게 물어요. SIL-64가 위키 기준을 5개로 고치면 이 차이는 없어져요.

## 7. 확인할 변경과 답

> 저장소는 이 절대로 동작해요 (착수 안내 v2, 10/12 팀 피드백, D51). Slack, 이슈 다시 열기, 답 취소는 만들지 않아요. 이슈(번호 형식, 담당자 바뀜 옮기기)는 알림 기능이 생길 때까지 그대로 둬요.

### 7-1. 언제 생기나

- 기준 하나가 바뀌면, 그 기준과 이어진 이슈마다 확인할 변경이 하나씩 생겨요 (notify.pending.one-per-issue).
- 완료된 이슈의 담당자에게도 가요. 이미 만든 결과물이 달라졌을 수 있어요 (notify.target.include-done).
- 기준을 바꾼 본인에게는 가지 않아요 (notify.target.skip-author).
- 확인하기 전에 같은 기준이 또 바뀌면 이전 것은 "새 버전으로 대체됨"으로 닫아요. 화면은 담당자가 마지막으로 본 버전과 최신 버전을 비교해 보여 줘요 (notify.pending.merge-versions).
- 새 값이 담당자가 마지막으로 본 값과 같으면 대기를 "자동 닫힘"으로 닫고 새 대기는 만들지 않아요. 되돌림이 아니라 같은 값으로 다시 저장해도 같아요 (notify.pending.close-on-revert).
  - 마지막으로 본 버전은 이렇게 정해요: 이 이슈에서 답한 건 중 가장 높은 버전 → 열린 대기 줄이 기억하는 버전 → 바로 앞 버전. 새로 생긴 기준이면 없어요 (notify.pending.last-seen-order). 담당자가 직접 저장한 버전은 세지 않아요.
- 이미 답했어도 값이 마지막으로 본 값과 다르게 바뀌면 다시 만들어요 (notify.pending.renotify-after-answer).
- 담당자가 없는 이슈와 바꾼 본인의 이슈는 통째로 건너뛰어요. 열린 대기 줄도 닫지 않아요 (notify.pending.no-owner, 착수 안내).
- 이슈 담당자가 바뀌면 답하지 않은 확인할 변경은 새 담당자에게 옮겨요. 담당자를 비우면 "담당자 없음"으로 옮겨요. 이전 담당자의 답은 그대로 둬요 (notify.pending.owner-change).

> 기준을 저장하거나 되돌리면 같은 트랜잭션에서 DB 함수 `on_standard_version_saved()`가 위 규칙대로 확인할 변경을 만들고 닫아요 (`20261012200000_last_seen_order.sql`). 규칙은 민수님의 `@sil/notify` `createPendingChecks`(팀 저장소 PR #7)와 같고, `supabase/tests/notify_rules.test.sql`이 그 테스트 12개와 같은 장면을 DB에서 돌려요 (D53). 앱·터미널에 바로 알리는 방법(SIL-65 조건 9)은 아직 정하는 중이에요.

### 7-2. 상태

| 상태          | 화면에 쓰는 말       | 뜻                                                          |
| ------------- | -------------------- | ----------------------------------------------------------- |
| `pending`     | 대기                 | 아직 답하지 않았어요                                        |
| `answered`    | 답함                 | 터미널이나 앱에서 답했어요                                  |
| `superseded`  | 새 버전으로 대체됨   | 같은 기준이 또 바뀌어서 최신 것으로 합쳤어요                |
| `auto_closed` | (화면에 나오지 않음) | 되돌려서 담당자가 마지막으로 본 값과 같아져 저절로 닫혔어요 |

상태는 이 네 가지예요 (10/12 피드백). 답을 기다리는 건 대기뿐이에요. 위키 data.pending.status-values는 아직 "답 취소"를 적고 있어요 (11절 12).

### 7-3. 답하는 법

```
이 변경이 내 일에 영향을 주나요?
├─ 관계있다 → 미리 알았나요?
│            ├─ 알았다
│            └─ 몰랐다 → (선택) 다시 해야 할 일 한 줄
└─ 관계없다 → 이유 한 줄 (100자 이하, 꼭 받아요)
```

- 두 질문은 주 지표 "몰랐다"를 세는 데 꼭 필요해요 (notify.answer.two-questions).
- "관계없다"의 이유는 이슈 연결과 적용 범위 중 무엇이 틀렸는지 알려 줘요 (notify.answer.unrelated-reason).
- 한 곳에서 답하면 다른 곳의 같은 알림은 답한 것으로 처리해요. 다른 곳에서 또 답하면 "이미 터미널에서 답했다"고 알려 주고, 화면은 그 알림을 조용히 닫아요 (notify.answer.one-place).
- 저장하는 값은 관계, 알았나(관계있다일 때만), 관계없는 이유, 답한 곳(터미널/앱), 답한 시각이에요. "수락/거절", "이미 알고 있었음"은 쓰지 않아요 (10/12 피드백).
- 완료된 이슈를 다시 열지는 묻지 않아요. 위키 v2에서 notify.answer.reopen-done을 폐기했어요. 저장 함수에는 인자가 남아 있지만 쓰지 않아요.
- "관계있다"고 답한 기준은 다음 세션부터 그 사람의 AI 작업 맥락에 들어가요. 진행 중인 이슈만, 최근 10개까지예요 (notify.answer.next-run-context).
- 확인 시간은 저장하지 않아도 돼요 (10/12 피드백). 잰다면 알림을 연 순간부터 마지막 답을 고를 때까지의 초예요 (data.response.check-seconds).

### 7-4. 실패했을 때

확인할 변경을 불러오지 못하면 다른 내용보다 먼저 "불러오지 못했다"고 알려요. 실패를 "변경 없음"으로 보여 주지 않아요 (notify.error.not-empty). 저장소의 읽기 함수는 실패하면 빈 목록 대신 오류를 돌려줘요.

## 8. 화면과 문구 지침 (디자이너용)

### 8-1. 화면

- 이번 범위에서 꼭 만들 앱 화면은 **"나에게 온 변경"과 답하기** 하나예요. 위키 화면과 지표 화면은 시간이 되면 만들어요 (app.screen.inbox-first).
- 확인할 변경은 한 화면에 하나만 보여 줘요. 답하면 다음 것으로 넘어가요 (notify.terminal.one-change).
- 알림 하나를 확인하는 시간은 중간값 1분 이내를 지켜요 (goal.guard.check-time). 다른 문서를 열지 않고 판단할 수 있어야 해요.
- 변경마다 보여 줄 칸 (notify.terminal.show-fields):

| 칸                | 어디서 오나                                                        |
| ----------------- | ------------------------------------------------------------------ |
| 기준 제목         | 기준 버전의 제목                                                   |
| 이전 값 → 지금 값 | 마지막으로 확인한 버전의 값 → 이번 버전의 값                       |
| 이유, 근거        | 이번 버전                                                          |
| 바꾼 사람과 시간  | 이번 버전                                                          |
| AI가 고쳤는지     | "AI가 고침", "PR에서 찾음" 표시 (detect.change.ai-mark)            |
| 되돌림인지        | "v1로 되돌림" 표시                                                 |
| 영향받는 이슈     | 이슈 번호와 제목. 연결이 없으면 "근거 없음" (notify.link.no-guess) |

- 상태 이름은 7-2의 "화면에 쓰는 말"을 그대로 써요. 코드에도 같은 표가 있어요 (`PENDING_CHECK_STATUS_LABELS`).

### 8-2. 앱 알림

> v2(SIL-65)에서 앱은 웹 + PWA로 바뀌었어요 (D50). 아래 Windows 앱 고유 ID, 자동 실행, 설치 경고 안내는 데스크톱 앱 기준이라 위키 v2(SIL-64)에서 고쳐요. 웹에서는 앱이 열려 있는 동안 Realtime 구독 + 브라우저 알림으로 띄우고, 앱을 닫았을 때까지 알리려면 Web Push가 필요해요.

- 확인할 변경이 생기면 앱이 바로 운영체제 알림을 띄워요. 따로 푸시 서버를 두지 않아요 (app.notify.realtime). DB 쪽 설정은 끝났어요.
- 알림을 누르면 "나에게 온 변경"이 열리고 그 변경이 선택돼요 (app.notify.click-to-inbox).
- 알림 제목은 공백 포함 40자 이하예요 (app.notify.title-length, 지금 v1).
- Windows에서는 앱 고유 ID를 설정해야 알림이 떠요. 앱은 컴퓨터를 켤 때 자동으로 실행돼요 (app.notify.windows-id, app.startup.auto-launch).
- 앱은 Mac과 Windows를 모두 지원해요. 정식 인증 없이 배포하고, 처음 열 때 뜨는 경고를 넘기는 방법을 설치 안내에 적어요 (app.platform.mac-windows, app.install.unsigned-guide).

### 8-3. 문구

- 변경 설명에는 개발 용어 대신 쉬운 말을 써요. 꼭 필요하면 처음 나올 때 괄호로 풀어 써요 (copy.explain.plain-words, 항상 적용).
- 이전 값과 지금 값은 같은 문장 구조로 한 문장씩 써요. 그래야 차이가 한눈에 보여요 (copy.explain.before-after).
- 변경 이유는 왜 바꿨는지만 한 문장으로 써요. 근거에 없는 영향은 추측해 쓰지 않아요 (copy.explain.reason-one).
- 터미널, 앱 화면, 앱 알림은 같은 정보를 같은 말로 써요 (copy.same-words.everywhere).
- 답은 "관계있다/관계없다", "알았다/몰랐다"로 불러요. "수락/거절"은 쓰지 않아요 (copy.term.related).
- 서비스 이름을 정하기 전에는 "이 도구"라고 불러요 (copy.term.this-tool).
- 기준 문장(제목, 값)은 "~이다 / ~한다"로 끝나는 평서문이에요. 해요체는 알림 문구에서만 써요 (기준 작성 원칙 5).

## 9. 기능을 붙일 때 쓰는 통로

다른 패키지는 DB를 직접 부르지 않고 core의 DB 함수만 써요. Node(MCP 서버, 명령어)는 `@sil/core/node`에서, 웹 앱은 브라우저에서도 도는 `@sil/core/data`에서 같은 함수를 가져와요 (D50). 주고받는 값의 타입은 [타입 명세](타입명세서.md)를 따라요.

| 누가   | 붙일 기능                         | 쓰는 것                                                                                                                                                                                                    |
| ------ | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 민수님 | 터미널 알림, 알리기 도구          | `listPendingChecks`, `saveAnswer`, `listIssues`. 확인할 변경은 DB 함수 `on_standard_version_saved()`가 이미 만들어요 (D51)                                                                                 |
| 신지님 | 앱 화면, 앱 알림                  | Realtime(`pending_checks`), `listPendingChecks`, `saveAnswer`, `isOpenPendingCheck`, `PENDING_CHECK_STATUS_LABELS`                                                                                         |
| 경하님 | 바뀐 기준 찾기                    | `saveStandard`(`aiDetected: true`, `source: 'code'`, 근거 필수), `matchesCodePath`·`searchStandardList`(적용 범위로 거르기). 거절 코드 `CHANGE_LIMIT`, `VERSION_CONFLICT`가 오면 PR 댓글로 사람에게 물어요 |

- 사람별로 무엇을 어디에 연결하는지는 부록 C에 자세히 적었어요.
- 응답 기록은 정해진 14칸이에요: 기록 시각, 기준 ID, 기준 버전, 바뀐 내용, 바꾼 사람, 근거, 이슈 번호, 담당자, 관계, 알았나, 확인 시간(초), 관계없다 이유, 모르고 계속했다면 다시 할 일, 기록한 방법 (data.response.columns). `sil export`는 도구가 남긴 답과 사람이 `answers.csv`에 적은 답을 한 표로 합치고, 기록한 방법 칸에 "도구" 또는 "사람"을 적어요 (data.response.method).
- 숫자는 비율만 쓰지 않고 "N건 중 M건"으로 보여 줘요 (goal.report.as-is). `sil export`는 주 지표, 5단계(바뀐 기준 → AI가 고침 → 알림 보낸 이슈 → 관계있다 → 몰랐다), 확인 시간 중간값, 관계없다 비율, 되돌린 비율을 이 모양으로 보여 줘요.

## 10. 매일 일하는 순서

1. 작업을 시작하면 AI는 목차를 먼저 읽고, 이번 작업과 관련된 영역만 열어요 (wiki.read.index-first).
2. 기준을 바꾸면 버전을 1 올리고 CHANGELOG 맨 아래에 한 줄 남겨요 (work.wiki.changelog). MCP로 저장하면 결과에 그 한 줄이 이미 만들어져 오고, AI가 `team-wiki/CHANGELOG.md`에 그대로 붙여요. 놓친 줄은 `pnpm sil changelog --append team-wiki/CHANGELOG.md`로 채워요.
3. 위키 파일을 고친 뒤에는 `python3 team-wiki/scripts/check_wiki.py team-wiki`로 형식을 검사해요.
4. Figma만 고친 날은 CHANGELOG에 직접 남기거나 #작업 채널에 "기준 변경:"으로 시작하는 한 줄을 남겨요 (work.wiki.figma-record).
5. DB 표를 바꿀 때는 이미 올린 파일을 고치지 않고 새 마이그레이션 파일을 더해요. 바꾼 규칙에는 `supabase/tests/`에 검사를 붙여요.
6. 결정은 Linear에 이유와 함께 적어요. Slack에는 링크만 남겨요. 의견이 갈리면 그 일의 DRI(최종 결정권을 가진 사람)가 정해요 (work.decision.linear-first, work.decision.dri).

### C-2. 모두가 지킬 약속

1. **사람 이름은 하나로 써요.** 등록 이름(`X-Sil-User`), 이슈 담당자, 바꾼 사람, 받는 사람, 답한 사람이 모두 같은 글자여야 해요: `정민`, `민수`, `신지`, `경하`, `부건`, `호윤`. 하나라도 다르면 "바꾼 본인에게는 보내지 않는다"가 틀려요. 등록은 `pnpm mcp:register --user 부건`처럼 해요.
2. **이슈 번호는 `#5` 모양이에요** (착수 안내, 8자 이하).
3. **DB는 core 함수로만 불러요.** 표에 직접 쓰지 않아요. 쓰기는 DB 함수가 형식을 검사해요. 타입은 `@sil/core`에서 가져오고 새로 만들지 않아요. 칸의 뜻과 "v2 밖" 값은 [타입 명세](타입명세서.md)에서 확인해요.
4. **키는 나눠 써요.** 팀원 PC의 Claude Code와 `sil brief`는 MCP 서버(주소와 팀 토큰)만 써요. Supabase 공용 키는 MCP 서버, GitHub Actions, 앱에만 둬요.
5. **오류 코드를 보고 다음 일을 정해요.** 전체 코드는 [타입 명세 7절](타입명세서.md#7-에러-errorsts와-규칙-상수-rulests)에 있어요.

| ------------------- | ----------------------------------------- | ------------------------------------------------- |
| `VALIDATION_FAILED` | 빈 칸, 모양이 틀림, 바뀐 내용 없음        | 문구대로 고쳐요. 사람에게 묻고 지어내지 않아요    |

```ts
export const listPending = defineTool({
  name: 'list_pending',
  title: '나에게 온 변경',

  inputSchema: z.object({}),
  annotations: { readOnlyHint: true },
  handler: async (_input, context) => {
    if (!context.user)
      throw new SilError(
        'VALIDATION_FAILED',
        '누구인지 몰라요. pnpm mcp:register --user 이름 으로 다시 등록해 주세요.',
      );
    const checks = await listPendingChecks({ recipient: context.user });
    return { count: checks.length, checks };
  },
});

// respond.ts
export const respond = defineTool({
  name: 'respond',
  title: '답하기',
  description:
    '확인할 변경 하나에 대한 사람의 답을 저장해요. 답은 사람에게 물어서 받고 지어내지 않아요. ...',
  inputSchema: z.object({
    pendingCheckId: z.string(),
    affected: z.boolean(), // 관계있다 true / 관계없다 false
    known: z.boolean().optional(), // 관계있다일 때 알았다 true / 몰랐다 false
    unaffectedReason: z.string().trim().max(100).optional(), // 관계없다일 때 한 줄
    elapsedSeconds: z.number().int().min(0).optional(),
  }),
  handler: async (input, context) => {
    const result = await saveAnswer({
      ...input,
      answeredBy: context.user ?? '',
      channel: 'terminal',
    });
    return {
      ...result,
      // SIL-67: 관계있다면 에이전트가 바뀐 기준을 다시 읽어요 (T5 "다시 읽었어요")
      next: input.affected

```

**SIL-64 위키 v2를 DB로 옮기는 순서.** SIL-64는 이 고침이 "우리 도구로 기록할 첫 번째 실제 변경"이라고 했어요. 그렇게 되려면 아래 순서를 지켜요.

2. 이슈 목록을 넣어요. `team-wiki/issues.csv`에 두면 `sil import`가 같이 읽어요. 칸은 아래와 같아요.

```csv
이슈 번호,이슈 제목,담당자,이슈 상태,기준 ID
#5,담당자에게 알리고 답 기록하기,민수,진행 중,app.notify.title-length
#7,앱 알림과 나에게 온 변경 화면,신지,진행 중,app.notify.title-length
```

- 이슈 상태는 `진행 중` 또는 `완료`예요. 기준 ID는 한 칸에 쉼표로 여러 개를 적어도 돼요.
- 예전 샘플의 `할 일` 상태는 진행 중으로 읽어요. 위키에 없는 기준 `notify.answer.skip-limit`에 걸린 연결은 지워요.

3. SIL-64 고침을 위키 파일에 하고 CHANGELOG를 남겨요 (출처: 회의). 그다음 `pnpm sil import --update --by 호윤`을 돌려요.
   - 바뀐 기준은 v2가 되고, 이어진 이슈의 담당자에게 확인할 변경이 생겨요 (D51).
   - 폐기는 파일의 `상태: 폐기`, `대체:`대로 처리돼요.
4. `check_wiki.py`가 적용 범위, 근거, 잠금을 비워도 되게 고쳐요. `sil import`는 이미 이 세 칸을 비워도 읽어요.
5. 샘플 데이터 v2의 모양은 core 타입(`PendingCheck`, `Answer`)과 예시(`packages/core/src/fixtures/coupon.ts`)를 따르면 저장소와 바로 맞아요.

**지표.** 데모 뒤에 `pnpm sil export`가 "관계있다 N건 중 몰랐다 M건"을 보여 줘요.
