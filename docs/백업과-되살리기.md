# 백업과 되살리기

팀 DB(Supabase)를 매일 백업하고, DB가 망가졌을 때 되살리는 방법이에요. 결정 사항 `wiki.backup.daily`("위키 데이터는 하루 한 번 백업하고, 팀이 함께 쓰는 공용 키에는 삭제 권한을 주지 않는다")를 코드로 옮겼어요.

## 한눈에 보기

| 항목             | 내용                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------- |
| 무엇을           | 표 7개 전체: 결정 사항, 버전, 이슈, 이슈 연결, 확인할 변경, 답, 충돌 보류                                |
| 언제             | 매일 03:00(한국 시각). GitHub Actions `backup` (`.github/workflows/backup.yml`), 손으로도 돌릴 수 있어요 |
| 어디에           | Actions 아티팩트 `sil-backup-<실행 번호>`, 7일 보관 (늘 최근 7번 치)                                     |
| 누가 열 수 있나  | `apps/cli/backup-keys/`에 공개 키를 올린 사람 (그 짝인 개인 키를 가진 사람)                              |
| 매일 확인하는 것 | 같은 실행 안에서 빈 Postgres에 실제로 되살려 보고, 표마다 줄 수가 같은지 봐요                            |
| 필요한 비밀 값   | `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` (detect.yml과 같은 값). 새 비밀 값은 없어요                   |

## 왜 필요한가요

- **Supabase 무료 플랜에는 자동 백업이 없어요.** 매일 백업은 Pro 플랜부터예요. Supabase 문서도 무료 플랜은 직접 내보내서 다른 곳에 보관하라고 권해요.
- **결정 사항은 지울 수 없게 막아 뒀지만, 그것만으로는 부족해요.** 프로젝트가 지워지거나, 잘못된 마이그레이션이나 SQL을 한 번 실행하면 되돌릴 방법이 없었어요.
- **예전 문서와 실제가 달랐어요.** 예전 코드 주석은 "backup.yml이 매일 돌리고 암호화한다"고 적었지만, 그 workflow는 저장소에 없었어요.

## 어떻게 만들었나요

| 고민                            | 고른 방법                                                                                                 | 이유                                                                                                                                                      |
| ------------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 무엇으로 읽나                   | 공용 키로 읽기만                                                                                          | `pg_dump`는 DB 주인 비밀번호가 필요해요. 그 비밀번호를 공개 저장소의 Actions에 두면 뚫렸을 때 DB 전체를 바꿀 수 있어요. 공용 키는 읽기와 저장 함수만 돼요 |
| 표를 읽는 사이에 누가 저장하면  | 표 7개를 두 번 연달아 읽어 똑같을 때만 받아요 (최대 5번)                                                  | 공용 키로는 여러 표를 한 번에 읽을 수 없어요. 그대로 두면 "버전은 있는데 그 확인할 변경은 없는" 백업이 생길 수 있어요                                     |
| 한 번에 1,000줄까지만 오는 제한 | 1,000줄씩 나눠 끝까지 읽어요                                                                              | 확인할 변경은 지울 수 없어서 계속 늘어요                                                                                                                  |
| 공개 저장소의 아티팩트          | 공개 키로 잠근 파일만 올려요 (RSA-OAEP로 데이터 키를 잠그고, 내용은 AES-256-GCM)                          | 아티팩트는 누구나 받을 수 있어요. 비밀번호 하나로 잠그면 그 비밀번호가 Actions에 있어야 해요. 공개 키 방식은 Actions에 여는 열쇠가 없어요                 |
| 되살리기                        | 백업을 SQL로 바꾸고 psql로 넣어요. 한 트랜잭션 안에서 표가 비었는지, 칸이 같은지, 줄 수가 같은지 확인해요 | 하나라도 틀리면 아무것도 넣지 않아요. 우리 명령은 DB 비밀번호를 받지 않아요                                                                               |
| 왜 저장 함수로 되살리지 않나    | 빈 DB의 표에 그대로 넣어요 (CLAUDE.md "표에 직접 쓰지 않는다"의 예외)                                     | `save_standard`를 거치면 버전과 시각이 새로 생기고 확인할 변경도 다시 만들어져서 기록이 달라져요                                                          |
| 정말 되살아나는지               | 매일 같은 실행 안에서 빈 Postgres 17에 되살려 봐요                                                        | 한 번도 되살려 보지 않은 백업은 믿을 수 없어요. 팀 DB와 마이그레이션이 어긋나면 이 단계가 먼저 알려 줘요                                                  |
| 새 패키지                       | 쓰지 않아요 (Node의 `node:crypto`, `node:zlib`만)                                                         |                                                                                                                                                           |

## 처음 한 번 할 일: 열쇠 만들기

1. 열쇠를 만들어요. 이름은 GitHub 아이디처럼 영어 소문자로 써요.

   ```bash
   pnpm sil backup-key <이름>
   ```

   - 공개 키 `apps/cli/backup-keys/<이름>.pub.pem`이 생겨요. PR로 올려요.
   - 개인 키 `~/.haribo/backup/<이름>.key.pem`이 생겨요. 저장소·채널·Actions에 올리지 않아요.

2. **개인 키를 비밀번호 관리자 같은 안전한 곳에 하나 더 보관해요.** 개인 키를 잃으면 그 키로만 잠근 백업은 아무도 열 수 없어요.
3. **두 명 이상이 열쇠를 올려요.** 받는 사람이 여럿이면 그중 누구의 개인 키로든 열려요.

공개 키가 하나도 없으면 매일 백업이 "잠글 공개 키가 없어요"로 실패해요. 잠그지 않은 파일은 올리지 않아요.

## 매일 백업 확인하기

- **실행 결과 보기:** GitHub → Actions → `backup`을 열어요.
  - 초록이면 백업과 되살리기 시험이 모두 통과한 거예요.
  - "되살리기 시험" 단계만 빨강이면 백업은 이미 올라가 있어요. 팀 DB와 `supabase/migrations`가 어긋났는지 먼저 봐요(칸이 다르면 표 이름과 칸 목록이 오류에 나와요).
- **손으로 돌리기:** Actions → `backup` → Run workflow.
- **받기:**

  ```bash
  gh run download <실행 ID> --name sil-backup-<실행 번호> --dir backup/
  ```

- **열어서 줄 수만 보기:**

  ```bash
  pnpm sil restore backup/<파일>.json.enc --key ~/.haribo/backup/<이름>.key.pem --check
  ```

## 되살리기 (DB가 망가졌을 때)

되살리기는 **빈 DB에만** 들어가요. 쓰고 있는 DB 위에 덮어쓰지 않아요.

1. **빈 DB를 준비해요.** Supabase에 새 프로젝트를 만들고 연결해요.

   ```bash
   pnpm supabase link --project-ref <새 프로젝트 ref>
   ```

2. **표와 함수를 올려요.**

   ```bash
   pnpm db:push
   ```

3. **되살리기 SQL을 만들어요.** 백업 시각, 원본, 표마다 줄 수가 먼저 나와요.

   ```bash
   pnpm sil restore backup/<파일>.json.enc --key ~/.haribo/backup/<이름>.key.pem --sql backup/restore.sql
   ```

4. **넣어요.** DB 주소는 Supabase 대시보드 → Connect에서 복사해요(DB 비밀번호가 필요해요).

   ```bash
   psql "<새 DB 주소>" -v ON_ERROR_STOP=1 -f backup/restore.sql
   ```

   - 끝나면 표마다 줄 수가 나와요. 백업의 줄 수와 다르면 SQL이 스스로 멈추고 아무것도 넣지 않아요.

5. **뒷정리해요.**
   - `backup/restore.sql`과 받은 백업 파일을 지워요. DB 내용이 그대로 들어 있어요.
   - DB 시간대를 다시 맞춰요. 마이그레이션에 없는 설정이라 새 프로젝트에는 빠져 있어요.

     ```sql
     alter database postgres set timezone to 'Asia/Seoul';
     ```

   - 새 DB 주소와 공용 키로 바꿔요: Cloud Run 비밀 값(`haribo-supabase-url`, `haribo-supabase-publishable-key`), GitHub Secrets(`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`), 각자의 `.env`.

### 내 컴퓨터에서 연습하기

workflow와 같은 순서예요. 임시 Postgres(포트는 아무거나)에 해요.

```bash
psql -d <빈 DB> -v ON_ERROR_STOP=1 -f supabase/plain-postgres.sql
```

```bash
for file in supabase/migrations/*.sql; do psql -d <빈 DB> -v ON_ERROR_STOP=1 -q -f "$file"; done
```

```bash
psql -d <빈 DB> -v ON_ERROR_STOP=1 -f backup/restore.sql
```

`supabase/plain-postgres.sql`은 Supabase에 원래 있는 역할 3개와 Realtime publication을 만들어요.

## 알아 둘 것

- **백업에는 표의 데이터만 들어가요.** 표·함수·권한은 `supabase/migrations`가 원본이에요. 마이그레이션 밖에서 바꾼 설정(DB 시간대 등)은 되살린 뒤 따로 해요.
- **백업 사이에 생긴 변경은 잃을 수 있어요.** 하루 한 번이라 최대 하루 치예요.
- **7일 안에 알아채야 해요.** 백업은 7일 뒤 사라져서, 8일 넘게 지나서 알아챈 문제는 되돌릴 백업이 없어요. 더 오래 남기려면 `backup.yml`의 `retention-days`를 늘려요 (공개 저장소는 최대 90일).
- **실패가 7일 넘게 이어지면 남은 백업이 하나도 없어요.** Actions → `backup`이 빨간색이면 바로 고쳐요. 실패 메일은 예약 시각(cron)을 마지막으로 고친 사람에게만 가요.
- **예약 실행이 멈출 수 있어요.** 공개 저장소에 60일 동안 활동이 없으면 GitHub가 예약 실행을 멈춰요. 멈추면 Actions → `backup`에서 다시 켜요.
- **표를 더하면 `BACKUP_TABLES`에도 더해요.** `packages/core/src/node/backup.ts`에 있고, 빠뜨리면 `backup.test.ts`가 마이그레이션과 비교해서 실패해요.
- **Supabase가 멈추는 것도 막아 줘요.** Supabase 무료 플랜은 7일 동안 쓰지 않으면 프로젝트를 멈추는데, 매일 읽어서 그것도 막아요.
