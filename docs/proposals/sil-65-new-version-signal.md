# SIL-65 조건 9: 새 버전이 저장된 것을 알리는 방법 (제안)

> **상태:** 제안. 민수님과 정해요. 정하면 SIL-65 조건 9를 체크해요.
> **작성:** 정민님 · **함께 정할 사람:** 민수님 (확인할 변경 만들기, 착수 안내 6)

## 한 줄 요약

**저장 함수가 새 버전을 쌓은 직후, 같은 트랜잭션 안에서 `on_standard_version_saved(기준 ID, 버전)`을 불러요. 민수님은 이 함수 본문에서 확인할 변경을 만들고, 앱은 확인할 변경 표를 Realtime으로 구독해요.**

자리는 이미 만들어 두었어요 (`supabase/migrations/20261009100000_v2_store.sql`). 10/12 팀 피드백에 맞춰 본문도 채웠어요 (`20261012100000_feedback_v2.sql`, D51). 이제 이 함수가 확인할 변경을 만들고, 이전 대기를 대체됨이나 자동 닫힘으로 닫아요. 남은 건 앱·터미널에 바로 알리는 방법이에요.

## 세 가지 방법 비교

|                    | **A. 저장 함수 안에서 바로 (추천)**                           | B. DB 이벤트를 구독해서 만들기                                | C. 저장한 뒤 MCP 도구가 부르기                         |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------ |
| 방법               | `on_standard_version_saved()` 본문에서 확인할 변경을 만들어요 | 서버가 `standard_versions` 새 줄을 Realtime으로 받아 만들어요 | `save_standard` 도구가 저장 뒤 알리기 함수를 불러요    |
| 빠짐없이           | **저장과 함께 성공하거나 함께 취소돼요** (검사 B4로 확인)     | 받는 서버가 꺼져 있던 동안의 변경은 놓쳐요                    | MCP를 거치지 않는 저장(PR 검사, `sil import`)은 빠져요 |
| 어느 길로 저장해도 | 같아요 (MCP, GitHub Actions, `sil import`)                    | 같아요                                                        | MCP로 저장할 때만                                      |
| 더 필요한 것       | 없어요                                                        | 늘 켜져 있는 서버 하나                                        | 없어요                                                 |
| 대가               | 만드는 규칙을 SQL(plpgsql)로 써요                             | 서버 두 대가 같은 변경을 받으면 중복으로 만들 수 있어요       | 저장은 됐는데 알림이 실패하면 둘이 어긋나요            |

A를 추천하는 이유: 우리 서비스가 막으려는 게 "바뀐 내용이 필요한 사람에게 닿지 않는 것"이라, 저장과 알림이 어긋날 틈이 없는 방법이 맞아요.

## A로 정하면 민수님이 할 일

새 마이그레이션 파일에서 함수 본문만 바꿔요 (이미 올린 파일은 고치지 않아요).

1. `issue_standards`에서 바뀐 기준과 이어진 이슈를 찾아요.
2. 예외 4가지 (착수 안내 6)
   - 담당자가 없는 이슈는 건너뛰어요.
   - 바꾼 사람(`standard_versions.changed_by`)과 담당자가 같으면 만들지 않아요.
   - 같은 이슈에 답하지 않은 이전 버전이 있으면 `superseded`로 닫아요.
   - 되돌려서 담당자가 마지막으로 본 값과 같아지면 `auto_closed`로 닫아요.
3. `pending_checks`에 한 줄씩 넣어요 (기준 버전 1개와 이슈 1개마다 한 줄). 표 이름은 팀 위키 용어.md를 따라 `pending_changes`에서 바뀌었어요 (10/9).
4. 앱 알림(A1)용 Realtime 설정은 `20261009200000_wiki_compat.sql`에 이미 들어 있어요. 앱은 `recipient = 내 이름`으로 걸러 구독해요.
5. 터미널(T2)은 Claude Code를 켤 때 `listPendingChecks({ recipient: 내 이름 })`로 아직 답을 기다리는 내 줄(대기)을 읽어요. 실시간 구독은 필요 없어요.
6. 답 저장은 `save_answer`, 잘못한 "관계없다" 취소는 `cancel_answer`가 이미 해요. 담당자가 바뀌면 `save_issue`가 남은 확인할 변경을 옮겨요.

> 팀 위키와 착수 안내가 다른 곳: 위키 `notify.pending.no-owner`는 담당자 없는 이슈도 "담당자 없음"(recipient null)으로 남기라고 하고, 착수 안내 6은 건너뛰라고 해요. 표는 둘 다 받을 수 있게 recipient를 비울 수 있어요. 어느 쪽으로 할지 정해 주세요.
