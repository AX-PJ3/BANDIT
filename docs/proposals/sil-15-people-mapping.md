> **상태:** 제안 (적용 보류). 10/12 오전 스펙 리뷰에서 정해요. 코드와 Linear 이슈에는 아직 반영하지 않았어요.
> **작성:** 정민님 · **함께 볼 사람:** 경하님, 민수님, 신지님(SIL-41 화면 정보 목록과 맞춰 보기)
> **꼭 챙길 점 (SIL-15):** 10/12 오전까지 확정해야 경하님, 민수님, 신지님이 시작할 수 있어요.

## 한 줄 요약

**Linear를 사람 명단의 원본으로 쓰고, 우리 표에는 Linear가 모르는 것(GitHub·Slack 아이디)만 더해요. GitHub 아이디는 각자 설치할 때 스스로 채워요.**
기능 코드는 표를 직접 보지 않고 `@sil/core`의 함수 4개로만 사람을 찾아요.

## 왜 필요한가요: 누가 무엇으로 사람을 찾나

세 기능이 서로 **다른 아이디**를 들고 같은 사람을 찾아야 해요. 사람 연결표는 이 아이디들을 잇는 표예요.

| 누가                       | 언제                     | 들고 있는 값 → 찾는 것                                                          | 이슈                   |
| -------------------------- | ------------------------ | ------------------------------------------------------------------------------- | ---------------------- |
| 경하님 (바뀐 기준 찾기)    | PR이 반영될 때           | PR 작성자의 **GitHub 아이디** → 고친 사람, PR 댓글로 물을 사람                  | SIL-24, SIL-26         |
| 민수님 (알리기)            | 기준이 바뀔 때           | 이슈 담당자의 **Linear 아이디** → 알릴 사람, 알릴 곳(터미널·앱·Slack)           | SIL-29, SIL-30, SIL-33 |
| 민수님 (알리기)            | 확인할 변경을 만들 때    | 고친 사람 ↔ 담당자가 **같은 사람인지** ("기준을 바꾼 본인에게는 만들지 않는다") | SIL-30                 |
| 민수님·신지님 (명령어, 앱) | Claude Code나 앱을 켤 때 | **이 컴퓨터의 나** → 나에게 온 변경                                             | SIL-28, SIL-42         |
| 신지님 (앱 화면)           | 화면을 그릴 때           | 사람 → 화면에 보일 이름                                                         | SIL-41, SIL-42         |
| 호윤님 (요약 화면)         | 저녁 확인                | 담당자 없음, 모르는 사람 목록                                                   | 흐름도 4               |

세 번째 줄이 핵심이에요. **GitHub(고친 사람)과 Linear(담당자)를 이어야** 본인 제외가 돼요. 연결표가 틀리면 본인에게 알림이 가거나, 반대로 알림이 빠져요.

## 채우는 방법 세 가지 비교

|                         | A. 한 사람이 다 적기                   | **B. Linear에서 가져오고 + GitHub은 각자 등록 (추천)**                                                              | C. 전부 자동 맞추기                                                    |
| ----------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 방법                    | 정민님이 6명의 아이디를 물어 표에 적음 | 이름·이메일·Linear 아이디는 Linear API로 가져오고, GitHub 아이디는 각자 `pnpm onboard` 때 `gh api user`로 자동 입력 | Linear 이메일과 GitHub 커밋 이메일을 맞춰 자동 연결                    |
| 처음 채우는 수고        | 10분 + 아이디 묻고 기다리기            | 정민님 1분 + 각자 30초 (설치 중에)                                                                                  | 0분                                                                    |
| 틀릴 가능성             | 오타, 대소문자                         | 거의 없음 (본인 계정에서 바로 읽음)                                                                                 | **조용히 틀림**: GitHub 이메일을 비공개(noreply)로 쓰는 사람은 안 맞음 |
| 다른 팀 3팀이 붙을 때   | 정민님이 병목                          | 각자 설치 명령 하나로 끝 (SIL-33 "10분 설치"와 맞음)                                                                | 맞지 않는 사람을 찾아 손으로 고쳐야 함                                 |
| 사람이 들어오고 나갈 때 | 손으로 고침                            | Linear에서 다시 가져오기                                                                                            | 다시 맞추기                                                            |

**B를 추천하는 이유:** 각자 자기 줄만 채우니 기다리는 사람이 없고, 아이디를 본인 계정에서 바로 읽어 틀릴 일이 없어요. 다른 팀이 붙을 때도 같은 방법이 그대로 통해요.

## 추천안 자세히

### 1. 표 모양 (SIL-15 초안에서 더하는 칸만 굵게)

| 칸            | 값          | 누가 채우나               | 왜                                                                        |
| ------------- | ----------- | ------------------------- | ------------------------------------------------------------------------- |
| **id**        | 내부 아이디 | 자동                      | 다른 표는 이 값으로 사람을 가리켜요. 아래 "함께 정할 것" 1번 참고         |
| 이름          | 표시 이름   | Linear에서                | 이름이 바뀌어도 Linear만 고치면 돼요                                      |
| 이메일        |             | Linear에서                | Slack 아이디를 찾는 열쇠. 공개 저장소면 파일에 저장하지 않아요            |
| Linear 아이디 |             | Linear에서                | 겹치면 안 돼요                                                            |
| GitHub 아이디 |             | **본인** (설치할 때 자동) | 소문자로 저장해서 비교해요 (GitHub은 대소문자를 가리지 않아요)            |
| Slack 아이디  |             | 이메일로 자동 (SIL-33 때) | 지금은 비어 있어도 돼요                                                   |
| **종류**      | 사람 / 봇   | 자동                      | `github-actions[bot]`, `claude[bot]` 같은 PR 작성자를 사람과 구분해요     |
| **사용 중**   | 예 / 아니오 | Linear에서                | 팀을 떠나도 지우지 않아요. 지난 기록의 "고친 사람"이 사라지면 안 되니까요 |

### 2. 채우는 순서

| 언제                                 | 누가                      | 무엇을                                                                                                                                      | 걸리는 시간 |
| ------------------------------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| 10/12 아침 전                        | 정민님                    | Linear 팀 "MVP 사일로" 구성원을 가져와 표를 만듦                                                                                            | 1분         |
| 각자 처음 설치할 때 (`pnpm onboard`) | 본인                      | 내 Linear 이메일로 내 줄을 찾고(못 찾으면 목록에서 고름), GitHub 아이디를 `gh api user`로 채움. "이 컴퓨터의 나"를 `.env`의 `SIL_ME`에 저장 | 30초        |
| 사람이 들어오거나 나갈 때            | 정민님 (나중엔 매일 자동) | Linear에서 다시 가져오기. 본인이 채운 GitHub 아이디는 덮어쓰지 않음                                                                         | 1분         |
| Slack 알림을 만들 때                 | 민수님                    | 이메일로 Slack 아이디를 채움                                                                                                                | 자동        |

`gh`가 없는 사람은 GitHub 아이디를 직접 한 번 입력해요.

### 3. 기능에서 쓰는 법: 함수 4개

기능 코드는 표를 직접 읽지 않고 아래 함수만 써요. **이 모양만 먼저 정하면, 표 저장 위치(DB)가 늦어져도 각자 오늘부터 코드를 쓸 수 있어요.**

| 함수                               | 쓰는 사람                    | 돌려주는 것                |
| ---------------------------------- | ---------------------------- | -------------------------- |
| `findPersonByGithub(login)`        | 경하님                       | 사람 또는 `null`           |
| `findPersonByLinear(linearUserId)` | 민수님                       | 사람 또는 `null`           |
| `getMe()`                          | 민수님 (명령어), 정민님 (앱) | 이 컴퓨터의 나 또는 `null` |
| `listPeople()`                     | 신지님 (이름 표시)           | 사람 목록                  |

못 찾으면 에러를 던지지 않고 `null`을 돌려줘요. 사람을 못 찾았다고 기준 변경이나 알림을 놓치면 안 되니까요 (아래 4번).

### 4. 못 찾거나 애매할 때

| 상황                                    | 처리                                                                             | 이유                                                |
| --------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------- |
| PR 작성자의 GitHub 아이디가 표에 없음   | 고친 사람은 비우고 원래 아이디를 근거에 남김. 요약 화면에 "모르는 사람"으로 표시 | 기준 변경을 놓치지 않는 게 먼저예요                 |
| 이슈 담당자가 표에 없거나 담당자가 없음 | 확인할 변경은 만들고 "담당자 없음"으로 표시                                      | 흐름도 "작업에 담당자가 있나?"와 같아요             |
| 봇이 올린 PR                            | 고친 사람 = PR을 **합친 사람**                                                   | AI가 고쳐도 책임지는 사람이 있어야 본인 제외가 돼요 |
| 이슈 담당자가 바뀜                      | 사람 표는 그대로. 확인할 변경을 만들 때마다 담당자를 **Linear에서 다시 읽음**    | 예외 4 (처리 안 한 변경은 새 담당자에게)            |
| 한 사람이 GitHub 계정 두 개             | MVP에서는 하나만                                                                 | 단순하게 가요. 필요하면 나중에 표를 나눠요          |

### 5. DB가 보류인 동안

- 표는 저장소의 파일 하나(예: `data/people.json`)로 둬요. PR로 고치니 누가 언제 바꿨는지 남아요. DB가 정해지면 같은 내용을 옮겨요 (SIL-21 갈아 끼우기).
- 저장소를 공개로 한다면 이메일은 파일에 넣지 않고, 필요할 때 Linear에서 읽어요.
- Linear API 키는 각자 `.env`의 `LINEAR_API_KEY`에 넣어요 (저장소에 올리지 않아요, SIL-18).
